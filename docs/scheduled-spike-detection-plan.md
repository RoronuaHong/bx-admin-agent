> 状态：**P1～P2.5 已落地**（分钟频率 + 仅异常通知 + 恢复 + 指令脚手架 + **先测后跑**）。2026-10-08 起破线不再按时间去重。
> 入口：http://localhost:5173/chat → 对话试跑 / 定时任务。
> 对齐：ChatGPT Monitoring +「先测后跑」。破线每期都推，恢复仍要连续 2 期正常。竞品对照见 `docs/scheduled-alert-best-practices-comparison.md`；会话落点见 `scheduled-task-sessions-plan.md`；总览见 `agent-infrastructure.md` §8。

## 0. 怎么做（最终口径）

**预警 = 通用定时任务的一种用法。**  
指标 / 阈值 / 窗口写在**指令**里；引擎只负责「多久查一次」和「破线才推、持续破线去重」。

### 0.1 主路径：先聊清楚，再挂预警

```text
① 对话里用自然语言说清盯什么、超多少算异常
② 试跑一轮，确认 [NORMAL] / [SPIKE] / [NO_DATA] 口径对
③ 「设为数据预警」→ 表单带入指令 / MCP / 预警默认
④ 确认频率与通知通道后保存
```

表单用于改频率 / 通知 / 编辑已有任务；「填入模板」只是骨架，不能替代试跑。

| 用户填 | 预警默认 |
|---|---|
| 名称 | — |
| 用途：周期报告 / **数据预警** | — |
| **指令** | 运行时追加 `[SPIKE]` / `[NORMAL]` / `[NO_DATA]` |
| **频率**（5/10/15/30 分钟） | 每 **10** 分钟 |
| **通知**：每期都推 / **仅异常时推** | 仅异常；`[SPIKE]` 每期都推；连续 2 期 `[NORMAL]` 补一条恢复。启用后第一期（立即执行或到点）不论结果都发一条启动确认 |
| 工具 / 结果落点 | 默认 **同一会话** |

业务阈值（如印度对话量 >300）只写在指令里，不进表单字段。

| 来源 | 学到的 | 我们怎么落 |
|---|---|---|
| **ChatGPT Monitoring** | 指令 + 频率 + meaningful 才推 | 用途=预警 + `on_alert` + 标记协议 |

## 3. 引擎行为

| 策略 | 行为 |
|---|---|
| `always` | 成功 / 失败都推 |
| `on_alert` | 失败仍推；成功看首行标记 |

- `[SPIKE]` → 每期都推
- `[NORMAL]` → 静默；曾告警且连续 2 期 → 推「已恢复」
- `[NO_DATA]` → 不推；保留 firing
- 还欠启动确认（新建、重新启用，或上一期通道没发出去）时，这一期不论标记都推。预警文案说明之后仅异常才推；已经破线时标题仍是异常。通道一条都没收到则记下待确认，下一期再试。
- 新建周期任务或预警会马上多跑一期（不改原 cron）。一次性任务不提前跑。文案按通知策略而不是用途标签：仅异常策略不写「之后每期都推」。

**取证失败时的正文由服务端按状态注入，不看模型措辞**（2026-09-30）：接地护栏纠正用尽仍没取到数据时，
那段正文是模型写的受约束诚实兜底，措辞每期都可能不同（实测出现过「没有实际取数」「未进行实际取数」）。
早期实现只在正文恰好等于确定性兜底文案时才补协议行 → 模型一自由发挥，预警正文就没有首行标记，
`parseAlertMarker` 认不出来，`marker` 落空，与「模型没遵守协议」无法区分。
现在判据是 `usage.ungrounded` 状态：预警正文换成 `[NO_DATA]` 协议句，报告正文保留原文、
由调度器按 `ungrounded` 记「未产出结论」（不再靠正文等于某句固定文案来判定，否则会记成成功并推空壳报告）。

`MINUTELY` 仅 5/10/15/30；相邻触发 <60s 拒绝。  
长跑结束后按**跑完时刻**推进 `nextRunAt`（避免 `*/5` 连环补跑）。

| 模块 | 职责 |
|---|---|
| `schedule-alert.ts` | 标记、投递决策、恢复、`SCHEDULE_ALERT_GUIDE` |
| `schedules.ts` | 持久化 / 锁 / tick；跑完后推进下一拍 |
| `app.ts` | 预警指引 + 摘图/导出 + 轮次上限 12；定时运行同时摘掉 `manage_schedule` |
| `chat.ts` | `omitBuiltinTools`；列表结果压缩 / 截断提示；直接翻页闸门 | 
| `list-count.ts` / `list-page-gate.ts` | 服务端按小时翻页计数；每个列表工具本轮只放行一次第一页 |
| `builtins.ts` | `manage_schedule` 支持 `purpose` / `notifyPolicy`；文案提示先测后跑 |
| `ChatPage.vue` | 用途 / 频率 / 通知；「设为数据预警」「从对话带入」 |

## 6. 验证建议

本机投递试跑只走固定测试通道 `dingtalk`（关键词 `bx-agent`）。不要打开印度业务通道 `ch_bb911ec0-6`。

1. 对话试跑 → `[NORMAL]` →「设为数据预警」→ 保存 → 侧栏可见。  
2. 空白「数据预警」表单：默认 10 分钟 / 仅异常 / 同一会话 + 先测后跑提示。  
3. 启用后第一期（立即执行或到点）不论 NORMAL / SPIKE / NO_DATA 都推一条启动确认；之后 NORMAL 不推；每一期 SPIKE 都推；两期 NORMAL 后恢复。暂停再启用会再发一次启动确认。  
4. 单次跑超过一个 cron 间隔后，不应立刻连环触发下一期。
5. 数据源取不到时：预警这一期的正文首行是 `[NO_DATA]`（运行记录里标记也是 NO_DATA、不推送）；报告这一期记「未产出结论」而不是成功。
