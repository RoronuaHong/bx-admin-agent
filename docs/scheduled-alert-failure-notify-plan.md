# 定时预警：执行失败不要每期刷通知

> 状态：**已落地**（2026-10-09）。`on_alert` 的执行失败按本文通知；破线仍每期都推。
> 触发：印度客服对话量预警在 2026-10-09 00:00–07:56 向钉钉连发「失败」。数据没有破线。检查没写完结论，引擎按失败每期推了一条。
> 对照：`scheduled-alert-best-practices-comparison.md` §1.1、§1.2、§5.3。破线每期都推的决定（2026-10-08）不动。

---

## 0. 最终方案（三件事一起做）

1. **业务破线和检查器故障分开通知。** `[SPIKE]` 仍每期都推。检查没跑完只在「刚失败」和「失败持续满 60 分钟」时各推一条，不每 5 分钟推一次。
2. **额度类错误立刻换模型，不对同一个模型空转重试。** 定时运行跳过已冷却的模型。
3. **预警轮次固定，不被交互自主度下调。** 调用方传入的预警上限保持原值。

不做：不把破线重新加冷静期；不把执行失败改记成 `[NO_DATA]`；不拆业务群和运维群；不把阈值做成表单字段；不让模型自己决定推不推。

---

## 1. 依据

| 来源 | 用到的规则 | 本方案怎么落 |
|---|---|---|
| ChatGPT Monitoring | 默认安静。只有有意义的变化才打扰。取不到就说明阻塞，不要猜 | 正常、无数据仍不推。失败通知说明「这次检查没完成」，不编会话量 |
| Datadog / 告警节奏 | 检测频率不等于通知频率。同一状态用再通知间隔，而不是每次检测都发 | 检测仍按 cron（5 分钟）。同一失败态 60 分钟内只发一条 |
| 本仓库 2026-10-08 | 破线不去重，每一期 `[SPIKE]` 都推；恢复仍要连续 2 期 `[NORMAL]` | 这条只覆盖业务破线，不覆盖模型 402/429 |
| 对照文档 §5.3 | 模型只打标，引擎决定推不推 | 失败态放在 `decideAlertDelivery`，不写进指令 |
| 千问办公执行记录 | 状态留在执行记录里；推送是给人看的摘要 | 运行记录仍逐期记 `failed`。钉钉只收合并后的失败通知 |
| WorkBuddy | 推送失败不改变任务成败 | 反过来也成立：任务失败不改写成成功，只减少重复推送 |

今早的事实：0:00–07:56 多数期没有结论文本，对话里是「（生成未产出内容）」，`on_alert` 把它们当成失败推到钉钉。原因是 Step-5 返回 402，OpenRouter 免费模型返回当日额度用尽；收尾调用没发出去。8:00 之后写出 `[NORMAL]` 的期没有再推。最后一条失败推送是 07:56。同期日志还有自主度把预警轮次从 12 降到 8，这些失败会让下一期更难写完。

## 2. 通知规则

`always`（周期报告）不变：成功、失败都每期推。

`on_alert`（数据预警）：

| 本期结果 | 运行记录 | 钉钉 |
|---|---|---|
| `[SPIKE]` | 成功，标记 SPIKE | 每期都推 |
| `[NORMAL]` | 成功，标记 NORMAL | 不推。告警中连续 2 期推「已恢复」 |
| `[NO_DATA]` | 成功，标记 NO_DATA | 不推。保留 firing |
| 没有结论文本，或模型调用失败后收束 | **失败**（不改成成功，也不写成 NO_DATA） | 见下面的失败态 |

失败态（只对 `on_alert`）：

- 上一期不是失败、这一期失败：推一条。标题用「失败」，正文说明这次检查没有完成，不要用「本次未产出内容」充当业务结论。原因详情留在该期对话里。
- 已经处于失败态：不推。
- 失败态持续满 **60 分钟** 仍失败：再推一条。然后重新计这 60 分钟。
- 任一期写出 `[SPIKE]`、`[NORMAL]` 或 `[NO_DATA]`：清除失败态。这一期按上表处理（破线照推，正常和无数据不推）。
- 启动确认仍按现规则：启用后第一期不论结果都推一条。失败态从这一期之后开始算。
- 已启用任务在表单里改了名称、任务内容、频率、用途、通知策略、结果落点或工具并保存：立刻向已启用通道推一条，正文写明当前这些配置和任务内容。只改未读数、暂停，或保存前后相同，不推。这条不是检查结果，不进入失败态，也不等下一拍 cron。发送失败不影响保存。

60 分钟按跑完时刻计算，不按 cron 拍数。5 分钟任务大约 12 期提醒一次，10 分钟任务大约 6 期提醒一次。

状态记在任务上，建议字段：`alertState.failingSince`（进入失败态的时刻；没有则未在失败态）、`alertState.failNotifiedAt`（最近一次失败通知的时刻）。不新做通知通道。

## 3. 模型调用

定时运行和交互对话共用自动换模时，额度错误会把整条链打满才失败。

- 400、401、402、403、404、408、413、422、429、500、502、503、504、529：这个模型本轮不再重试，立刻换下一个仍可用的候选。超时和网络中断仍可重试当前模型。
- 402、当日免费额度用尽的 429、401、403、404、500 额外进入冷却。其它 429，以及 400 / 408 / 413 / 422 / 502 / 503 / 504 / 529 只换模型，不冷却。
- 所有候选都因这些状态码失败时，钉钉**每一期**都推。状态行写状态码，正文写对应原因（鉴权失败、没有权限、模型不存在、额度或权限不足、请求过于频繁、请求不被接受、请求过大、无法处理、超时、过载、网关或服务异常）。不套用 60 分钟合并。
- 没有状态码、只是没写完结论的失败，仍按失败态合并：刚失败推一条，满 60 分钟再推一条。
- 定时运行选模时跳过冷却中的模型。候选都不可用时，按第 2 节记失败并走失败态，不要为了换模把本期拖到数分钟。
- 不在引擎里写死「印度任务必须用某一个模型」。要固定模型，配在该任务或该对话的模型上。

## 4. 预警轮次

`chat.ts` 里 `autonomyFor` 会把调用方传入的 `maxRounds` 再往下收。预警任务传入的上限（默认 12，`MCP_SCHEDULE_ALERT_MAX_TOOL_ROUNDS`）是无人值守预算，不再交给自主度下调。交互对话仍按现有自主度收紧。

周期报告的轮次预算维持现状。

## 6. 验收

1. 没有状态码的执行失败连续 3 期：钉钉只收到第 1 条；运行记录 3 条都是失败。模型 402 / 429 / 500 / 502 / 503 / 504 每一期都推，并写明状态码。
2. 失败持续满 60 分钟：再收到 1 条；未满 60 分钟不追加。
3. 下一期 `[NORMAL]`：不推。再失败时重新按「刚失败」推一条。
4. 连续两期 `[SPIKE]`：两期都推。
5. `[NO_DATA]`：不推，运行记录不是失败。
6. 周期报告失败：仍每期推。
7. 预警运行的日志里不再出现轮次从 12 降到 8。
