## 0. 结论先行

1. **本项目这次没有给出任何业务数字。** 四个子问题（日活、会员、渠道、退订）全部“未生成”。根因不是数据取不到，而是工具预算用完了：31 次调用里 28 次在读技能、查表结构、看字段取值，只有 3 次真正执行 SQL。总调用上限 `MCP_MAX_TOTAL_TOOL_CALLS=30` 一到就被强制收尾。
2. **本项目这次还有一处接地错误。** 第 20 步 `countryCode` 字段说明里写着“91 印度、55 巴西”，技能里也写了，但回答却说“代号与国家名的对应关系本轮未取到”，于是只按代号呈现。
3. **WorkBuddy 给出了完整答案，结构和可操作性明显更好，但有 5 处会影响结论的口径问题**（见第 3 节）。最严重的一处：它把“首次充值”当作“新增会员”，用“首充 − 到期”去算净增，进而得出“月净增 +8.5 万、近一周转降”。本仓库技能已记录“首充 ≠ 新增会员，实测可差 5 倍”。所以**会员到底是增是降，目前还没有在存量口径上被证实**。
4. **仓库里已有的“真值”彼此矛盾，不能直接拿来当裁判**：
   - 10-17 印度有效会员一份是 773,370，另一份是 741,999。条件更严的那份（多了 `status=0`）反而更大，说明至少一个查询有问题。
   - 巴西有效会员一份是 26，一份是 28。
5. **方案核心（对齐业界做法）：**
   - 先把 6 个指标写成指标契约，并沉淀为“已验证查询”；
   - 智能体优先调用已验证查询，不再每次从表结构摸索；
   - 再配合“分开计预算、子问题覆盖闸、存量瀑布对账、黄金集回归”四项运行时改动。

## 3. WorkBuddy 的准确性问题（按影响排序）

| # | 问题 | 影响 | 应该怎么说 / 怎么做 |
|---|---|---|---|
| W1 | **“新增” = 首充**（`rechargeType=3 & isFirst=1`），“净增” = 首充 − 到期 | 首充里混有本来就是会员的赠送 / 试用转付费账号，它们不会让存量增加；回流会员（以前是会员、断过又回来）则完全没算。净增 ≠ 存量变化，“月净增 +8.5 万、10-05 周转负”的方向不可靠 | 按业界“存量瀑布”：期末存量 − 期初存量 = 新开通 + 回流 − 流失，必须能对平；首充单列为“付费转化” |
| W2 | 流失没有剔除**赠送 / 试用 / 兑换码会员到期**（`rechargeType` 0 / 4 / 5 / 6 / 9 …） | 免费会员到期会被算成“退订”，流失和“老会员不续费”的结论被放大 | 流失按“最后一次开通的来源”拆成付费到期未续 / 免费到期 / 退款 |
| W3 | “长周期老会员到期不续、年付到期”是**从平均在网时长推出来的假设** | `elt_user_vip_recharge_log.days` 能直接给出套餐时长，没有用；“年付”未被证实 | 用最后一笔开通的 `days` 分月付 / 季付 / 年付；没查就标成“假设” |
| W4 | 关联 `elt_user_full` **没有限定快照分区**（该表按 `recordDate` 分区、设备级） | 同一账号可能在多个分区、多台设备上带不同国家码，导致重复或错国；这可能也是两份历史真值 77.3 万 / 74.2 万对不上的原因 | 先建“账号 → 国家”映射：最新分区、`uid>0`、每个账号一个国家，并报告多国冲突账号数 |
| W5 | 10-14 日活用 “≈3,300,000” **估算填空**；10-12 部分周当整周写进结论 | 非查询结果进入表格和结论 | 不完整日 / 周要么剔除，要么单列并按日速度表述，不能填估算值 |
| W6 | “日活人数”其实是**设备数**，而且是 `elt_user_active`（使用时长表），与仓库其它地方用的 `elt_active_guid` 不同 | 读者会把设备当人；与其它报表对不上 | 标题写“日活设备数”，并注明表名；权威表需要数据团队拍板（见第 8 节） |
| W7 | 获客渠道没说取的是哪个字段（会员表 `appChannel`？设备当前 `apkChannel`？首访渠道 `elt_ap_channel`？） | 设备当前渠道 ≠ 购买时的获客渠道 | 写明字段和归因规则（首次付费时的渠道 / 首访渠道） |
| W8 | 巴西和印度并列成“两国” | 39 人样本，任何占比都是噪声 | 单列并标样本量（本项目已有“小基数隔离”护栏） |
| W9 | “近一周”是 10-08 ~ 10-14，周表却按周一切分 | 两个“近一周”数字不可比 | 统一用自然周或滚动 7 天，并在标题注明 |

WorkBuddy 的长处（应吸收）：

- 结论先行；
- KPI 卡片 + 逐日 / 逐周序列 + 渠道 + 流失分群 + 行动建议，完整闭环；
- 合计自检；
- 主动说明放弃过期预聚合表；
- 写出“踩坑证据句”（123 万 → 75.4 万）；
- 把“新增端”和“流失端”分开看，思路正确，只是口径要换。

## 4. 必须向用户说明的口径差异

1. **会员存量**：要不要加 `status=0`、`endDate > now()` 还是 `≥`、要不要包含赠送 / 试用会员。
2. **新增会员**：首次开通会员 vs 首次付费（首充）。两者可以差数倍。
3. **流失**：付费到期未续 vs 所有会员到期（含免费）；是否有宽限期；续费晚了算不算流失后回流。
4. **日活**：设备 vs 账号；`elt_active_guid` vs `elt_user_active`；时区 Asia/Shanghai；当天不完整。
5. **国家**：`elt_user_full.countryCode` 是电话国家码，不是 IP 所在地；账号在多台设备上国家码不一致时怎么取。
6. **获客渠道**：首访渠道 / 付费时渠道 / 设备当前渠道，三者结论可以不同。
7. **时间窗**：近一月、近一周是滚动窗口还是自然周 / 月；是否剔除当天。

## 7. 待执行的核验 SQL（草案，未执行）

全部只读；`elt_active_guid` / `elt_user_active` 每段 ≤ 10 天；先按 1~3 天小窗跑通再放大。

**① 账号 → 国家映射（以下所有按国家拆分的指标都复用它）**

```sql
WITH latest AS (SELECT max(recordDate) AS d FROM film_report.elt_user_full)
SELECT uid, any(countryCode) AS cc, uniqExact(countryCode) AS cc_n
FROM film_report.elt_user_full
WHERE recordDate = (SELECT d FROM latest) AND uid > 0
GROUP BY uid
-- 先报告 cc_n > 1 的账号数；为 0 才能直接用 any()
```

**② 当前有效会员（两种条件都跑，差异写进口径段）**

```sql
SELECT uc.cc,
       uniqExactIf(v.uid, v.status = 0) AS active_status0,
       uniqExact(v.uid) AS active_any_status
FROM film_report.elt_user_vip_info v
JOIN (/* ① */) uc ON uc.uid = v.uid
WHERE v.vipType = 2 AND v.endDate > now() AND uc.cc IN (91, 55)
GROUP BY uc.cc
```

**③ 历史存量与瀑布（用开通流水重建，替代不存在的 `startDate`）**

```sql
-- 在基准时刻 D 的会员 = 存在一笔开通记录满足 createdTime <= D < endTime（vipType=2，剔除 rechargeType=12 退款）
-- 取 D0 = 2026-09-18 00:00、D1 = 2026-10-18 00:00（Asia/Shanghai），得到集合 S0、S1
-- 新开通 = S1 − S0 且 D0 之前没有任何开通记录；回流 = S1 − S0 且 D0 之前有记录；流失 = S0 − S1
-- 对平检查：|S1| − |S0| = 新开通 + 回流 − 流失；|S1| 还要与 ② 在 D1 的结果相差 < 1%
```

**④ 流失分类**：对 S0 − S1 中的每个账号，取它在 D1 之前最后一笔开通记录的 `rechargeType`（付费 / 赠送 / 兑换码 / 退款）和 `days`（套餐时长），再关联 `elt_film_order.orderType`，区分新购和续费。

**⑤ 日活**：按天 `uniqExact(guid)`（设备）以及按天 `uniqExact(uid)`、`uid > 0`（账号），两张活跃表各跑 3 天做对照，剔除当天。

**⑥ 首充（付费转化）**：沿用 WorkBuddy 口径，但单列为“付费转化”，不参与净增计算。

## 8. 方案

### P0：先把数做准（1~2 天）

1. **执行第 7 节核验 SQL。** 产出一份带 `verified_at` 的真值表，替换两份历史文档里互相矛盾的数字，并回写 WorkBuddy 结论哪些成立、哪些不成立。
2. **修正技能文档。** 删除 `startDate`；改正“1.6 倍”；补“国家映射必须限定最新分区、每个账号一个国家”；补“流失要剔除免费到期和退款”；补“不完整日 / 周不得估算填空”。
3. **为 6 个指标写指标契约**，放在 `skills/business-data-query/metrics/`：会员存量、存量瀑布、流失分类、付费转化（首充）、日活（设备 / 账号）、获客渠道。每份写明实体、条件、时间窗、时区、排除项、去重键、来源表、核验 SQL、`verified_at`。

### P0：智能体运行时（与上面并行，2~3 天）

5. **预算分开计。** 元数据类调用（`read_skill` / `get_database_schema` / `get_field_values` / `list_*` / `search`）单独计“探索预算”，例如 12 次；`TOTAL_TOOL_CALL_CAP` 只计取数调用。总量命中时，如果还没有任何指标查询，不强制总结，而是追加一轮“只允许执行查询”的提示（改动点：`chat.ts` 的 `forceSynthesisByToolCallTotal` / `shouldForceSynthesisRound`）。
6. **子问题覆盖闸。** 多子问题的取数请求，先让模型列出子问题清单；收尾前检查每个子问题至少有一次指标查询，或写明为什么查不了。没覆盖的子问题优先分配剩余预算，而不是直接收尾。
7. **反向接地核验。** 回答里出现“未取到 X”，而工具结果里其实有 X（例如字段说明里的国家映射），判定为未接地，回补一轮修正。
8. **存量瀑布对平与“事实 / 假设”标签。** 回答里出现净增 / 下降结论时，必须带对平结果；没对平就降级为“初步”。归因类叙述没有维度查询支撑的，统一标成“假设”。

### P1：报告结构与回归（1 周）
