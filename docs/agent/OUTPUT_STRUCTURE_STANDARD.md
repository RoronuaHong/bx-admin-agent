# 通用输出结构标准（分析 / 数据类回答）

> 适用范围：本 Agent 在「工具模式」下、面向**多子问题 / 跨源取数**的长分析或报告类回答。
> 设计目标：**通用型（不绑定任何业务域） + 准确性（口径可追溯） + 稳定性（跨次调用结构可复现）**。
> 本文件是**生产规范兼设计依据**：先在此定稿，再落地到 `system-prompt.ts` 与 `chat.ts`（代码改动后置）。

## 0. 设计依据（最新最佳实践，2026）

- **报告骨架**：结论先行的执行摘要（倒金字塔）+ 数据与方法透明 + 结果解读 + 局限；用清晰标题 / 小结框 / callout 保证可扫描性。（Sona, 2026-03，《How to Write About Data Analysis》）
- **口径预定义**：关键指标应在披露段以「指标 / 计算口径 / 数据来源 / 解读方向」成表，避免后端口径漂移。（盈海数据, 2026-03）
- **通用与稳定**：优先用**显式输出契约（零样本）**而非大量少样本示例；少样本示例易对「手边便利样本」过拟合；结构稳定性靠**契约 + 校验闭环**而非模型自觉；用**留出测试集 + schema 合法率**度量，不对单一标杆过拟合。（Beehive Strategy, 2026-06）
- **可解释性**：生产级提示要求回答含「依据」比例强制 100%。（DevPress 提示工程可靠性设计, 2025）
- **表现层对照（已泛化）**：同类分析产物（WorkBuddy 报告, 2026-10）在「可扫描性 + 口径随数字走 + 关键洞察高亮 + 口径段含去重陷阱反例」上表现突出，本标准的表现层模式据此泛化，不复制其业务内容。

## 1. 适用范围与门禁（通用，不过度）

- 完整「总分总 + 口径段」仅当：**工具模式开启** 且 回答属于「多子问题 / 跨源取数 的长分析或报告」。
- 单一指标 / 简单问答：轻量形态——第一句结论 + 口径、第二句来源、第三句只写影响解读。
- 纯闲聊 / 零工具：不注入任何结构骨架（避免噪声）。
- 全程**零业务词、纯占位符**（`<库>.<表>`、`<字段>=<值>`、`COUNT(DISTINCT <键>)`），符合「禁止写死」红线，任何业务域通用。

## 2. 通用报告骨架（总 → 分 → 总）

对齐 Sona 六段 + 盈海执行摘要，落地为三段式，并吸收表现层对照的成熟模式：

### 总（执行摘要 · 结论先行，倒金字塔）
- **元信息行（一句话，开头）**：数据来源 + 分析区间（含时区）+ 生成时间。溯源前置，不等到结尾口径段才说。
- **核心结论**：1 段或 3–5 个要点，每点 = **结论句（粗体）+ 关键数字 + 口径**，按「目的 → 核心发现 → 关键数据 → 建议」顺序。
- **KPI 小结卡（可选，强推荐）**：每个核心指标用「标签 / 数值 / 口径注释」三联卡呈现，口径随数字走（可扫描性 + 口径在点上）。
- 不写技术细节，只给结论与影响。

### 分（按子问题 / 维度分述）
- 每个子问题一章；维度可时间 / 地域 / 渠道 / 人群 / 模块等（占位，不写死）。
- 每章：表格或图 + 该章关键数字的**字段级口径**标注；区分 **result（发生了什么）** 与 **insight（为什么重要）**。
- **关键洞察用 callout / alert 高亮**：对转折、异常、人群分型等最关键结论用醒目框（如「净增转负的触发点是新增端而非流失端」），提升可扫描性与决策可读性。

### 总（数据口径与方法 · 收尾，准确性核心）
见第 3 节。

### 结论与行动（可并入执行摘要或单列）
- **结论与建议分开**；建议**可行动 + 按优先级排序**（避免「结论」与「下一步」混为一谈）。

## 3. 「数据口径与方法」段规范（准确性）

每个分析 / 报告类回答**必须**在结尾含此段。用占位符，不写死业务：

1. **数据来源**：库 / 系统 / 表（`<库>.<表>`）；复用既有定义 / 卡片优先于重算。
2. **字段级口径**：每个关键数字标注取数字段与过滤条件（`<字段>=<值>`、`<字段> 范围`）。
3. **去重 / 计数法**：明确 `COUNT(DISTINCT <键>)` / `uniqExact(<键>)` 还是 `COUNT(*)`；说明是否被设备级 / 多行放大而虚高。**可附反例**（如「曾误得 X、正确去重后 Y」）增强可信度。
4. **时间窗与不完整周期**：左闭右开裸列范围，标注时区；**不完整当天 / 部分周期必须显式标注或剔除，不得静默混入均值 / 环比 / 占比**（两种处理都合规，但不得偷偷算进去）。
5. **层级**：设备级 vs 账号 / 用户级，明确用的是哪个。
6. **近似与冲突**：估算 / 近似口径显式标出；多口径冲突**主动披露以哪个为准、为什么**，不混入。
7. **事实与推断分离**：实测值 vs 推断 / 假设，分别标注，不把推断当事实。
8. **故障 ≠ 缺数**：上游报错（5xx / 超时 / 连接失败）如实说「查询失败，没能取到」；**不**译成「库里没有 / 数据源没这个数」。
9. **未答子问题**：写清「哪个子问题 + 试过哪些来源 + 每个来源缺什么 + 需要补什么数据」，不允许只写「库里没有」带过。
- **双重披露**：口径既在点上的 KPI 卡 / 表注出现，也在末尾口径段汇总，便于审计。
- **页脚溯源声明**（推荐）：如「数值均来自实时查询、非抽样估算、可与明细交叉验证」。

## 4. 稳定性保障（工程侧；代码改动前置约定）

好结构「没沿用下来」的根因是它只活在 few-shot，而真正产出最终答案的合成 / 收尾轮没有硬指令。以下为落地点与现状（2026-10-17 已落地，见 §8）：

- **4.1 契约优先（已实现）**：结构权威来源 = 系统提示 `system-prompt.ts` 的 `ANSWER_SHAPE_EXAMPLE`（`tooling` 门控、每轮注入、**不依赖 `read_skill`**）；合成轮主指令 `chat.ts` 的 `WRAP_UP_HINT` 新增结构硬指令，覆盖主循环合成轮（用户消息）与 fallback 合成轮（系统提示）两条路径。零样本即生效。
- **4.2 校验闭环（部分已实现）**：`wrapUpWith` 新增 `hasCaliberSection` 检测，分析类长回答缺「数据口径与方法」段时回补一轮（对齐 `grounding` 事后核验）。主循环合成轮为流式输出，由提示契约保障，未做二次回补（避免缓冲整段回答）。
- **4.3 口径纪律不靠运气（已由现有机制覆盖）**：`ANSWER_SHAPE_EXAMPLE` 在 `tooling` 为真时恒注入，已含口径与来源、合计一致、关键数字标口径、末尾附「数据口径与方法」段等；无需额外「检测到 bi 再注入」逻辑。
- **4.4 避免过拟合（度量建议）**：用留出测试集 + schema 合法率（最终回答含「执行摘要」+「数据口径与方法」段的比例）做回归，不对单一标杆（如某国家 / 某业务）过拟合；少样本示例只在契约失效时按代表性补充。

## 5. 反模式（不可为）

- 把示例当硬结构、对便利样本过拟合（同一题两次回答结构相反）。
- 数字无口径（「销售提升了」而非「同比 +20%」）。
- 静默把不完整当天 / 部分周期混入均值 / 环比 / 占比（自相矛盾）。
- 口径只在末尾汇总、点上（KPI/表）不标（可追溯性差）。
- 设备级计数当人数（一号多机系统性虚高）。
- 故障译成缺数。
- 子问题答不了只写「库里没有」。
- 强行 JSON / 模板输出牺牲流畅。

## 6. 评估指标（可度量，对齐最佳实践）

- **schema 合法率**：最终回答含「执行摘要」+「数据口径与方法」的比例（主指标）。
- **口径字段覆盖率**：关键数字中标注口径的比例（含点上 KPI 卡 / 表注 + 末尾汇总）。
- **格式一致性**：同一题多次调用输出结构相似度（Beehive：同模型多跑 ≥5 次）。
- **准确性**：数字符合事实 / 业务规则的比例（可解释性强制 100% 含依据）。
