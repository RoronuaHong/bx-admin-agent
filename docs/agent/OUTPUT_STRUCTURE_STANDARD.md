# 生产输出结构标准（数据准确率 + 总分总）

> 本文件为**生产级输出规范**，基于本项目实测：
> - 标杆样本：用户提供「印度 / 巴西 会员与日活分析报告.html」（Metabase MCP 取数生成，结构见下）
> - 现有机制：`system-prompt.ts` 工具纪律、`grounding.ts`（零证据兜底 `decideGrounding` + 事后核验 `shouldRunVerification`）、`chat.ts` 的 `wrapUp` 综合轮
>
> **本文件不是外部框架的原文引用，不虚构依据。** 与 Deep Agent（LangChain）架构的对齐，是理念层面的对应，非逐字照搬。

## 一、对齐 Deep Agent 架构的落点

Deep Agent 核心是 *single coherent reasoning*（规划 → 执行 → 综合）。我们 `chat.ts` 已是「轮次循环取数 + `wrapUp` 综合轮」的形态。本规范的落点：**综合轮输出应呈现「总分总」**，让结论连贯、可追溯——这正是 Deep Agent 综合形态的对齐点。

- 规划（总）→ 执行（分）→ 综合（总）在运行时已存在；缺的是**输出呈现层**的结构约束。
- 数据准确率的根在 `grounding`（取数真相），本规范只补「呈现层」，不替代 grounding。

## 二、两条铁律

1. **数据准确率**：所有数字必须来自工具真实返回（已有 `grounding` + 事后核验保障）。
2. **总分总结构**：长分析 / 报告类回答采用 **总（核心结论）→ 分（明细 / 证据）→ 总（结论与行动）**。

## 三、总（核心结论）形态

- 开头给「核心结论」：每条 = **粗体结论句 + 关键数字 + 口径**。
- 标杆样本示例：
  > 「印度是绝对主力，巴西可忽略。印度当前有效会员约 754K、日活约 360万~400万；巴西当前会员仅 39 人、日活约 90 人/天。」

## 四、分（明细）形态

- 按子问题分章节（日活 / 会员 / 渠道 / 归因）。
- 表格列名用中文（`label-dictionary.ts` 已做多语言翻译层）；枚举值翻译为中文。
- 关键数字下方标注计算口径（字段 / 过滤条件）。

## 五、口径与方法（重要，新增要求）

报告 / 分析类回答建议附「数据口径与方法」说明：

- **数据源**：库 / 表。
- **指标口径**：每个指标用哪个字段 + 哪个值（如 `vipType=2 & endDate≥now()`）。
- **计算陷阱披露**：如连接键须 `COUNT(DISTINCT uid)`，否则因设备行放大而虚高（标杆样本曾误得 123 万，正确去重后 75.4 万）。
- **口径冲突主动取舍**：存在多个数据源 / 口径时，说明以哪个为准、为什么，**不混入冲突口径**（标杆样本：早期预聚合表覆盖不全，不作为主口径）。

## 六、总（结论与行动）

- 结尾给「结论与行动建议」：总结核心发现 + 可行动建议。

## 七、不可为（不乱改边界）

- 不强行 JSON / 模板输出（牺牲流畅、弱模型卡壳）。
- 不依赖报告漂亮判断正确性（根在 grounding 取数真相）。
- 运行时不做「首句含数字」等启发式强制判定（易误伤）。

## 八、代码落地位置

- `system-prompt.ts` 的 `ANSWER_SHAPE_EXAMPLE`：升级为显式「总分总 + 口径冲突披露 + 数字标口径」规则（见下条修订）。
- 数据准确率机制（`grounding.ts` / `chat.ts` `wrapUp`）：**保持不变**。

## 九、针对本次测试的验收预期

用户 query（经 chrome-devtools）：
> 帮我查下，目前印度、巴西的日活人数和会员数近一个月和近一周的获客渠道是怎么样的，还有就是分析下会员数下降的原因是哪些会员退订的？

优化后预期结构：

1. **核心结论（总）**：印度 vs 巴西量级对比（印度主导、巴西可忽略）；近一月净增为正、近一周转降；下降主因 = 老渠道长周期会员到期不续 + Google 系首月即走；头部 4 渠道集中度风险。
2. **分章节**：① 日活（DAU）近一月/近一周明细 + 解读；② 会员数（新增/流失/净增）按周；③ 获客渠道分布；④ 下降归因（哪类会员退订）。
3. **口径与方法**：数据源、会员/DAU 口径、连接键去重陷阱、多口径取舍。
4. **结论与行动（总）**：总结 + 行动建议（治理 Google 系早期流失、降低渠道集中度风险）。

每个数字须带口径；若取数不足如实说明，禁止编造。
