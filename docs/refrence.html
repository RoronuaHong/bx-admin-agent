AI Agent 企业落地知识手册

一、什么是企业级AI Agent

Agent 不是增强版聊天机器人。核心价值：把大模型自然语言理解，变成跨多系统自动执行任务的数字员工。

生产级Agent标志：有状态 State、Checkpoint断点恢复、HITL人工介入、Skill安全层、完整审计日志。

二、企业Agent标准架构（LangGraph体系）

前端输入(query、userId、tenantId) ↓ graph.invoke(state) 进入LangGraph ↓ Node1：意图识别LLM节点 ← 薄Prompt 输出action + params 写入State ↓ add_conditional_edges 条件路由 ↓ Skill业务节点（安全核心）   • 鉴权   • Pydantic参数校验   • 租户、软删除硬编码   • 调用 API / MCP‑Server / NL2SQL(只读)   • 写操作强制HITL人工确认 ↓ 结果回写State → Checkpoint快照落盘 ↓ Node2：LLM组装回答节点 ↓ 返回前端聊天框

组件分工

  • LLM：大脑，做理解、意图、结构化输出，不执行业务。
  • LangGraph：编排内核，State、Node、Edge、Checkpoint、HITL。
  • Skill：安全业务Node；参数校验、鉴权、异常捕获；不把敏感数据存入State快照。
  • Tool：最小原子能力；裸工具，不直接交给LLM调用。
  • MCP：外部资源标准化协议；仅在Skill内部调用，MCP本身不带安全防护。
  • Prompt(薄)：只约束输出格式；安全逻辑全部写代码，不靠提示词。

三、当前项目落地形态（bx-admin-agent）

对外产品形态已经调整为多 Agent 门户：用户先进入一个统一主页面，再选择具体 Agent。当前首批入口包括：后台管理 Agent、知识库 / RAG Agent、观影助手 Agent，以及后续更多 Agent 的预留位置。

  • 门户层是产品入口：负责展示 Agent 卡片、入口切换、全局 UI 语言 / 主题，不等同于服务端总控编排。
  • 后台管理 Agent：当前唯一完整可用的业务 Agent；登录后进入其独立工作台与会话页。
  • 知识库 / RAG Agent：当前先以产品入口 / 方案占位的形式挂到门户，用于承接制度、流程、知识库、文档检索类能力。
  • 观影助手 Agent：当前同样先以产品入口 / 方案占位的形式挂到门户，避免“文档有、页面没有”的错位。
  • Trace：现调整为门户级独立入口，放在 Header 中按权限展示；路径独立于后台管理 Agent，但当前仍依赖统一登录体系和 canViewTrace 权限投影控制访问。

当前项目已经落到可运行的 M1 形态：一个主聊天编排 + 多个 Worker 配置，而不是多个完全独立进程中的子 Agent 同时协作。

  • Supervisor 负责总控：接收用户问题，先做结构化理解，再决定是否需要路由。
  • Worker 负责领域上下文：例如 backend-api、knowledge；每个 Worker 都带自己的 system prompt、工具白名单和环境约束。
  • 未路由时只开放 META 工具：让模型先明确方向，再进入领域工具，避免一开始就误调接口。
  • 环境显式化：test / prod 会话态持久化，生产写操作继续要求确认。
边界说明：门户层解决“用户先进入哪个 Agent、看到哪些入口”的产品问题；Supervisor + Worker 解决“后台管理 Agent 内部如何路由与执行”的运行时问题。两者是上下两层，不应混为同一个“总 Agent”。
补充说明（2026-09-07）：当前项目已经把 Trace 从“后台管理 Agent 二级页”收敛为“门户级观测入口 + 权限控制”。也就是说，/trace 的产品归属在门户层，但是否显示、是否可进入、接口是否返回数据，都统一由 canViewTrace 控制。当前这层权限先通过服务端投影输出，支持 TRACE_ALLOWED_OWNERS（账号白名单）、TRACE_DENIED_OWNERS（账号黑名单）与 TRACE_ALLOWED_COUNTRIES（国家线白名单）做组合收紧；判定顺序为黑名单优先，其次 owner / country 任一 allow 命中即可放行。同时权限返回结构已开始抽象为门户级 entries 视图，为后续 Knowledge / Viewing / 更多 Agent 入口复用做准备。前端也补了登录回跳（next=/trace）与拒绝原因回传（deniedSource / deniedFrom），避免“被挡回去但不知道为什么”。

四、结构化意图层：不要只靠模型“看起来懂了”

企业 Agent 的关键不是让模型会说，而是让执行层拿到稳定、可消费、可拦截的结构化信号。当前项目通过 submit_understood_intent 承接这层能力。

字段 含义 作用
isBusinessRequest 是否属于业务请求 区分闲聊 / 业务处理
operationType read / write / unknown 与写操作确认策略联动
responseMode execute / clarify / explain-capability 决定继续执行、先澄清，还是只做能力说明
confidence 0~1 置信度 给后续重试提示和观测稳定性提供信号
missingSlots 当前缺失的关键槽位 帮助执行层提示模型先补问题，不盲目 call_api
典型例子：“我想找某个影片的剧集，该怎么做？” 这种问法应识别为 explain-capability，优先说明系统支持方式，或提示还需要影片名称 / ID，而不是直接调列表接口。

五、两种访问数据库方案对比

方案1：Skill调用业务API（业务操作首选）

LLM输出action+业务参数；Skill调用预开发HTTP/gRPC接口；SQL由后端开发预写ORM/模板。

  • ✅ 业务口径可靠，安全在接口层
  • ✅ 支持增删改写操作，配合HITL
  • ❌ 新查询需求需要开发新接口，灵活性低
  • 适用：后台业务、工单、订单、人员操作

方案2：NL2SQL直连数据库（仅限只读查询）

LLM生成SQL字符串，Skill内部做七层防护后，执行在只读副本库。

硬规则：生产环境禁止NL2SQL执行 INSERT / UPDATE / DELETE / DROP。写操作走API+Skill+HITL。

NL2SQL七层防护

  1. 数据库账号：独立只读副本，仅SELECT权限，使用数据库视图屏蔽敏感字段。
  2. Schema管控：只向大模型提供允许访问的表/视图元数据。
  3. AST语法解析校验(sqlglot)：拦截高危语句，表白名单，禁止多语句。不靠关键词字符串匹配，不靠Prompt约束。
  4. AST自动改写SQL：强制追加租户过滤条件，防止越权。
  5. 资源限制：SQL超时、最大返回行数，防止慢SQL打垮库。
  6. 完整审计日志：用户、会话id、原始提问、生成SQL。
  7. 结果层：敏感字段脱敏，截断超长结果。
对比项 调用业务API模式 NL2SQL直连只读库
AI输出 action + 业务params 完整SQL文本
SQL来源 开发预写ORM/模板 大模型动态生成
灵活度 低，受接口能力约束 高，自由组合统计查询
业务口径 高可靠 存在AI理解错误风险
写操作支持 ✅支持(HITL) ❌严禁
典型场景 业务后台Agent 内部BI、自然语言问数助手

六、AI Agent主要应用方向与前景

1）企业内部数字员工（当前最大市场）

  • 自然语言取数助手(NL2SQL只读)
  • 跨系统工单、CRM、权限编排助手
  • IT运维Agent（高危操作人工确认）
  • 财务法务文档解析、报表生成

2）SaaS产品内置Agent能力

不替换原有系统；增加自然语言入口，调用产品原有工具接口。例如IDE Agent、CRM智能助手、低代码AI工作流。

3）垂直行业智能体

金融投研、制造故障排查、电商客诉处理等。高风险动作必须人工复核。

4）C端个人Agent（成熟度偏低）

大多停留在信息问答；系统权限管控是难点，全自动执行操作产品较少。

技术演进路线

  • 过去：Function‑Call，无状态单次调用工具。
  • 现在：有状态Agent(LangGraph/AutoGen)，强调可控、审计、HITL。
  • 短期1‑2年：MCP协议普及；MCP‑Server会变多，但依然要封装Skill安全层。
  • 远期：多智能体协作；工程复杂度高，大规模生产落地尚少。
就业机会：最大机会不是训练大模型，而是Agent应用工程落地：LangGraph编排、Skill安全封装、RAG、MCP对接、NL2SQL防护、权限审计。后端开发可转型Agent应用工程师。

七、现实瓶颈 & 哪些场景不适合Agent

  • 幻觉没有彻底解决，安全逻辑必须代码硬写，不能依赖Prompt。
  • 多步Agent Token消耗高；简单固定流程优先传统接口。
  • 高风险写操作，Agent只能给建议，必须HITL人工确认。

不适合上Agent的场景

  1. 流程高度固定、输入输出确定：直接写业务接口。
  2. 希望Agent全自动执行高危写操作，无人工复核。
  3. 追求100%零人工全自动业务，企业现实中大多是人‑Agent协同。

八、项目当前进度说明

  • M1 路由链路已接通：Worker 选择、工具白名单、环境透传、会话态记忆已落地。
  • submit_understood_intent 已扩展支持 responseMode、confidence、missingSlots。
  • 针对说明型问法已增加防误执行策略：当模型判为 clarify 或 explain-capability 时，不应继续 call_api。
  • 多语种评测脚手架已预留，但目前按迭代安排默认关闭，不作为当前主线交付项。
  • 门户 Header 已增加按权限显示的 Trace 入口；独立路由为 /trace，不是 /agents/admin/trace 的产品主入口。
  • Trace 权限链路已经闭环：服务端投影 canViewTrace，并支持账号白名单 / 黑名单、国家线白名单；前端按权限显示、受控页未登录时登录后回跳、无权限时回门户并展示拒绝原因。
  • 前端工作台已开始做低风险拆分：聊天页的富文本渲染、会话存储恢复、后台任务恢复、标签菜单定位等逻辑已抽成独立模块，目标是降低单文件复杂度而不改原有交互。
  • 前端包体已同步治理：聊天页图表改按需异步加载，echarts / zrender / 富文本依赖已拆为独立 chunk，避免聊天首屏被观测与图表能力拖慢。
  • 前端最小回归闸门也已补上：apps/web/scripts/chat-helpers.test.ts 覆盖标题回退、缓存读写、消息清洗和流式事件归并；根 pnpm test 已串上这条前端回归。

九、面试口述速记

企业Agent核心是利用编排框架做有状态任务，Skill作为安全层。
访问数据库分两种模式：业务操作用API模式；数据分析可以NL2SQL只读，做多层AST防护，禁止写SQL。
Agent适合开放多变的复杂任务；简单固定流程优先传统接口；高风险操作强制人工介入。
