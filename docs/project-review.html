1 · 项目定位与技术栈

一句话：给内部管理后台配一个能用自然语言办事的 Agent——能查真实业务接口、能改代码仓库、能生成图表与 Excel/PDF 产物、能定时跑任务并推送结果。

定位边界

是不是
自研 Agent harness（工具循环、上下文工程、护栏全在自己手里）不是 LangChain / LangGraph 应用（无相关依赖，循环是自己写的）
多模型网关适配（OpenAI 兼容协议 + per-role agent 行为开关）不是单一模型 SaaS 封装，额度/限流可降级到候选链下一个模型
MCP 客户端宿主（可挂载任意 stdio / HTTP MCP server）不绑定某家 MCP 市场，凭据本地 .data/mcp-servers.json
信任域内多设备防串台（owner cookie）不是认证体系，无登录密码，别对外多租户

技术栈

服务端 apps/agent-server

  • Hono + @hono/node-server：HTTP 框架与 Node 服务
  • TypeScript + tsx：直接跑 TS 源码，PM2 托管
  • MongoDB Driver：会话/消息/任务/定时任务/技能开关持久化
  • MCP SDK（@modelcontextprotocol/sdk）：stdio / Streamable HTTP 两种传输
  • exceljs / pdfmake / docx：产物导出
  • mammoth / unpdf / exceljs：知识库文档解析
  • croner：定时任务调度

前端 apps/web

  • Vue 3（SFC + Composition API）+ Vite
  • 原生 fetch + ReadableStream 消费 NDJSON 流（不用 EventSource，因为要 POST 且要自定义头/断线续传）
  • 图表：ChartCard.vue 内置渲染（含 G2 系图表类型）
  • Markdown：自研渲染 chat-richtext.ts + md-tables.ts，前端 sanitize
  • i18n：自研 tx() 四语函数（中/英/葡/印地）

  • 语义是「信任域内防串台」，不是认证：cookie 可复制
export function resolveOwner(c: Context): string {
  const existing = getCookie(c, OWNER_COOKIE);
  const fromQuery = String(c.req.query("owner") || "").trim();
  if (OWNER_RE.test(fromQuery)) { /* 写回 cookie */ return fromQuery; }
  if (existing && OWNER_RE.test(existing)) return existing;
  const owner = randomUUID(); setCookie(...); return owner;
}

四条关键护栏的实现意图

① 同轮去重 vs 跨轮熔断

去重：比较 name|argsJson 全等签名，只执行第一个，其余回灌提示「已合并，需要更多数据请基于分页信息再调」。
熔断：跨轮签名相同累积到阈值 → 强制收束。
两者都不理解语义，纯协议层，所以不会误伤「正确递增分页」的调用。

② 结果治理 governToolResults()

超预算时把较早结果替换成占位文案；可被 TOOL_RESULT_PROTECT_PATTERNS 保护的结果不清理。另一条路是 offloadToolResult()：把大结果写进工作区文件 results/<callId>_<tool>.txt，模型可 fs_read 取回。

③ 伪调用协议护栏 looksLikePseudoToolCall()

弱模型爱把工具调用写成正文文本（JSON / XML / 方括号 / action:"工具名"）。这里只识别「工具调用写成文本」这一协议形态，不做语义分类；命中就丢弃 + 回灌规则。
边界业务/闲聊判定一律交模型，服务端不做词形写死。

④ 接地护栏 grounding.ts

「需要真实数据的问题」如果本轮零工具数据却出了结论 → 作废文本 + 回灌纠正提示（提示里写明两条路径：去取数 / 本就不需要数据则如实回答，由模型判定）。用尽仍无数据 → 走「受约束的诚实兜底」，禁止事实性断言。

知识点（对齐业界）：这四条分别对应 Cursor / Claude Code 的 dedup + doom loop + context offload + no-evidence guard。业界的共识是：护栏做在协议层（可预测、可观测），语义判定交给模型；一旦护栏里塞了业务正则，加一个场景就要改一次代码。

子代理 task 工具

父代理可 task 派生子代理：独立上下文 + 最小工具集，结果裁剪到 SUBAGENT_RESULT_CHARS 后回灌父上下文；并行上限 SUBAGENT_MAX_PARALLEL，可单独取消（POST /chat/subagent/:conversationId/:subagentId/cancel）。用于「派一个子代理去探 schema，只把结论带回来」这类上下文隔离场景。

两段式系统提示

23 · 知识点清单（点卡片看最佳实践对比）

每张卡片都可点击（或聚焦后回车）打开弹窗，内含业界常见做法 → 本项目做法 → 是否最佳实践 → 偏离原因 → 何时改回去五段对比。✅ 最佳实践⚠️ 有意偏离🐞 已知缺陷

执行 / 推送解耦✅

后台任务 + 事件缓冲，HTTP 连接只是订阅者

业界常见做法
早期很多实现把 req.signal 透传给生成器，连接断开即中止生成。新一代 Agent 服务（含 OpenAI Responses 的 background 模式）把「任务」做成一等公民，连接只是订阅者。
本项目做法
chat-tasks.ts 维护 RunningTask（事件缓冲 + AbortController），后台消费者驱动 chatStream；SSE 连接只转发；收束结果写回会话。
判定
✅ 与最佳实践一致。
为什么重要
用户刷新页面不会丢失结果；断线可续传；同会话重连不会开出第二个任务交错写消息。
何时改回去
无需改。若要跨进程水平扩展，把任务状态从内存 Map 换成外部存储即可，现接口不用动。
事件 seq 游标续传✅

任务内单调 seq，支持按游标补发

业界常见做法
SSE 的 id: + 重连 Last-Event-ID；OpenAI Responses 流式事件的 sequence_number。两者本质相同：给事件编号以便断点续取。
本项目做法
事件信封带任务内单调 seq，GET /chat/task/events?from=<seq> 补齐未收事件；taskId 防跨任务串流。
判定
✅ 与最佳实践一致，且两种业界口径都对齐了。
为什么重要
网络抖动是常态而非异常，续传把「重连 = 重问一次」变成「重连 = 接着看」。
何时改回去
无需改。
Prompt Cache 静态前缀✅

静态引导放 system 首位，动态提示走 user 追加

业界常见做法
把稳定内容（系统指令、工具纪律）放在提示最前并保持逐字节不变，这样多轮之间前缀可命中缓存（Anthropic cache_control / OpenAI 前缀自动缓存）。
本项目做法
staticGuide（工具调用纪律、规则、技能索引）作为 system 首条；重试/观察/纠正等动态提示以 user 消息追加，不污染前缀。
判定
✅ 与最佳实践一致。
为什么重要
工具循环里同一请求会调模型 N 次，前缀稳定才能重复利用缓存，直接省 token 与延迟。
何时改回去
无需改。注意：别把「当前时间」这类每轮变化的内容塞进静态段。
上下文卸载 offload✅

大结果写工作区文件，模型按需 fs_read 取回

业界常见做法
Claude Code / Cursor 把大工具结果卸载到虚拟文件系统，只在上下文里留摘要与路径，模型需要时再读。
本项目做法
offloadToolResult() 写 results/<callId>_<tool>.txt；另一条更早的结果是占位化（TOOL_RESULT_CLEARED）。
判定
✅ 与最佳实践一致。
为什么重要
「截断」会丢信息，「卸载」不丢——只是换个地方，且 usage 事件会显示被卸载条数，行为可见。
何时改回去
无需改。
历史压缩分层✅

prune（零成本）→ 必要时 LLM 摘要 → 缓存复用

业界常见做法
Cursor /summarize、Claude Code /compact：先把低价值内容（长表格、重复代码块）折叠/截断，仍超预算才做一次摘要。用户可见历史 ≠ 模型实际 token。
本项目做法
pruneHistoryTurns（表格超行折叠、长文本保头尾，零模型调用）→ 仍超才 summarizeHistory；结果缓存进会话，HISTORY_MAX_TURNS=8 保留最近原文。
判定
✅ 与最佳实践一致。
为什么重要
直接全量摘要既费钱又丢细节；先 prune 能把「必须总结」的触发点显著推后。
何时改回去
无需改。
去重 + Doom Loop 熔断✅

同轮去重管重复，跨轮熔断管死循环

业界常见做法
把「完全相同的调用」视为无信息量行为并合并/拒绝；对跨轮重复签到-like 行为设阈值熔断（「doom loop」一词即来自此）。
本项目做法
签名只用 name|argsJson：同轮相同只执行第一个；跨轮累积到 DOOM_LOOP_MAX_ROUNDS=3 强制收束。
判定
✅ 与最佳实践一致。
为什么重要
签名不含语义，所以「page 1→2→3 正确递增」不会被误伤——这是纯协议层护栏才做得到的。
何时改回去
无需改。护栏里一旦加入「看起来像分页」的判断，就开始误伤了。
接地护栏 grounding✅

零证据的结论作废 + 回灌纠正 + 诚实兜底

业界常见做法
检索增强场景要求答案可溯源；无证据应降级为「不知道」，而不是生成合理数字。Agent 领域把这条叫 anti-hallucination guard。
本项目做法
grounding.ts：本轮零工具数据却产出结论 → 作废文本 + 回灌纠正提示（给模型两条路径：去取数 / 本就不需要数据则如实回答，由模型判定）；用尽仍无数据则走受约束兜底，禁止事实性断言。
判定
✅ 与最佳实践一致，且比「硬性要求必须调工具」更灵活（允许模型判断本题本就不需要数据）。
为什么重要
Agent 最贵的错误不是报错，而是「看起来很合理的假数据」。
何时改回去
无需改。
协议护栏 vs 语义判定✅

只拦「工具调用写成文本」，意图判定交模型

业界常见做法
Cursor 的 <tool_calling> 约束是「必须走工具通道、禁止用文本模拟工具调用」，但没有「查询类不许反问」这类语义条款。
本项目做法
服务端只识别 JSON/XML/方括号/action 形态的伪调用；业务 vs 闲聊、意图、是否反问全部由模型决定，禁止写死词形正则。
判定
✅ 与最佳实践一致（且踩过反面：早期写过「问候句式/功能词」正则，把模型空间压死）。
为什么重要
护栏塞业务正则 → 每加一个业务场景就要改一次代码，且永远追不上。
何时改回去
不需要。若将来想更严格，正确手段是改提示词，不是加正则。
Deferred 工具检索⚠️ 有坑

工具过多时只留 search_tools 入口（TOOL_SEARCH_MODE=auto）

业界常见做法
工具数量爆炸时按需加载（deferred / tool search），避免工具 schema 吃掉大量上下文。
本项目做法
工具定义超窗口比例（TOOL_SEARCH_RATIO=0.1）才切 deferred；TOOL_SEARCH_MODE 必须保持 auto。
判定
⚠️ 做法正确但有已知副作用：弱模型不会主动检索就直接凭记忆作答 → 编造。
偏离说明
因此对强依赖工具的角色（movie）单独开了 forceEagerTools 走 per-role 强制全量注入，而不是全局改成 off——全局改会改变通用大模型的行为。TOOL_SEARCH_MODE=off 是红线。
何时改回去
当主用模型足够可靠地会主动 search_tools 时，可取消 per-role 例外。
子代理上下文隔离✅

独立上下文 + 最小工具集 + 结果裁剪

业界常见做法
Deep Agents 的 subagent：把「探查大量原始结构」的工作隔离出去，只把结论带回主上下文。
本项目做法
task 工具派生子代理：独立上下文、最小工具集、结果裁剪到 4000 字符、并行上限 3、可单独取消。
判定
✅ 与最佳实践一致。
为什么重要
避免把一次性探索的原始结构永久占用主上下文。
何时改回去
无需改。
Fail-closed 写确认✅

一次性票据 + 会话绑定 + 超时即拒

业界常见做法
写操作二次确认，默认保守；凭证不可重放；超时按拒绝处理（fail-closed）。
本项目做法
ticket 一次性且与会话绑定；必须先注册 waiter 再发事件（否则前端秒确认会失败）；未声明风险级别的工具一律需确认；批准/拒绝/超时都落审计。
判定
✅ 与最佳实践一致。
为什么重要
宁可让用户多点一次，也不要「点了拒绝却执行了」。
何时改回去
无需改。
不可信内容围栏✅

nonce 围栏 + 伪造标签中和 + 控制字符剥离

业界常见做法
把第三方文本（网页、检索结果、上传文档）标记为不可信输入，并用随机分隔符防止内容伪造边界；必要时限制模型把它当作指令。
本项目做法
untrusted.ts：[untrusted_content nonce=…] 包裹；同形开闭标签被中和成全角括号；stripDangerousControls 剥离控制字符并返回数量。
判定
✅ 与最佳实践一致。
为什么重要
边界靠机制而非「求模型分辨」——和 iframe sandbox / CSP 是同一思路。
何时改回去
无需改。
诚实失败 > 坏交付✅

  • 看 usage 事件里的 rounds / modelRetries / modelFallbacks / toolFusions / pseudoCallRetries / groundingRetries，先判断是哪一层在兜圈子

25 · 红线与工程纪律

① 「全部由大模型判断」

服务端不做语义正则预判：问候句式、功能词、中文参数键、JSON 字段名功能词都不许写死。
允许：协议结构护栏、数量/循环护栏、HTTP 方法、英文 CRUD 契约词、通用字典（id→ID）。

② 禁止业务词写死

代码逻辑/正则/映射表/配置/工具描述/错误提示/示例一律不许出现具体业务词，示例用 XX / <模块> / <接口> 占位。
豁免：mock 与「实时扫源码」的特例，严格隔离。

③ MCP / 数据库只读

BI 库不执行任何写 SQL；不改任何 MCP 服务器配置、工具清单、凭据。只读查询、列元数据、取值域是可以的。

④ 「删」≠「去掉显示」

用户说「去掉」「别显示」时，指的是隐藏展示（如在技能面板不列出），绝不删功能文件。索引、加载路径、校验白名单保留全量。

⑤ 提交纪律

改动完成后先给用户看，不自动 commit / push；只在用户明确要求时才提交。

⑥ 诚实优先

查不到就如实说查不到，不用训练记忆或其他域数据补全；额度/限流失败如实降级；未配置的能力如实说不可用。
