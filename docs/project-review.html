1 · 项目定位与技术栈

一句话：给内部管理后台配一个能用自然语言办事的 Agent——能查真实业务接口、能改代码仓库、能生成图表与 Excel/PDF 产物、能定时跑任务并推送结果。

定位边界

是不是
自研 Agent harness（工具循环、上下文工程、护栏全在自己手里）不是 LangChain / LangGraph 应用（无相关依赖，循环是自己写的）
多模型网关适配（OpenAI 兼容协议 + per-role agent 行为开关）不是单一模型 SaaS 封装，额度/限流可降级到候选链下一个模型
MCP 客户端宿主（可挂载任意 stdio / HTTP MCP server）不绑定某家 MCP 市场，凭据本地 .data/mcp-servers.json
信任域内多设备防串台（owner cookie）不是认证体系，无登录密码，别对外多租户

技术栈

服务端 apps/agent-server

  • Hono + @hono/node-server：HTTP 框架与 Node 服务
  • TypeScript + tsx：直接跑 TS 源码，PM2 托管
  • MongoDB Driver：会话/消息/任务/定时任务/技能开关持久化
  • MCP SDK（@modelcontextprotocol/sdk）：stdio / Streamable HTTP 两种传输；另内置 GitLab MCP（@zereight/mcp-gitlab）
  • exceljs / pdfmake / docx：产物导出
  • mammoth / unpdf / exceljs：知识库文档解析
  • croner：定时任务调度

前端 apps/web

  • Vue 3（SFC + Composition API）+ Vite + vue-router（多 Agent 门户：/ 门户、/chat 通用助手、/movie 观影助手、/support 客服助手）
  • 原生 fetch + ReadableStream 消费 NDJSON 流（不用 EventSource，因为要 POST 且要自定义头/断线续传）
  • 图表：ChartCard.vue 内置渲染——统计类走 G2、图形类（网络/拓扑等）走 G6，图表类型清单同源于 @bx/shared 避免两端漂移
  • Markdown：markdown-it 渲染 + DOMPurify 白名单 sanitize（chat-richtext.ts）+ md-tables.ts 表格修复；sanitize 属性钩子必须挂 afterSanitizeAttributes
  • i18n：自研 tx() 四语函数（中/英/葡/印地）

六条关键护栏的实现意图

① 同轮去重 vs 跨轮熔断

去重：比较 name|argsJson 全等签名，只执行第一个，其余回灌「本轮已执行过相同调用」。
熔断：跨轮签名相同累积到阈值 → 强制收束。
这两条都不理解语义，所以 page 1 与 page 2 不会被当成重复调用。
另一条是 list-page-gate.ts：每个列表工具本轮只放行一次第一页（只认 index / offset / page / cursor 这些页码形状，不认业务词）。跨页计数走 count_list_by_time，其它汇总走 run_tool_code。按 id 取详情不拦。

② 结果治理 governToolResults()

超预算时把较早结果替换成占位文案；可被 TOOL_RESULT_PROTECT_PATTERNS 保护的结果不清理。另一条路是 offloadToolResult()：把大结果写进工作区文件 results/<callId>_<tool>.txt，模型可 fs_read 取回。

③ 伪调用协议护栏 looksLikePseudoToolCall()

弱模型爱把工具调用写成正文文本（JSON / XML / 方括号 / action:"工具名"）。这里只识别「工具调用写成文本」这一协议形态，不做语义分类；命中就丢弃 + 回灌规则。
边界业务/闲聊判定一律交模型，服务端不做词形写死。

④ 接地护栏 grounding.ts

本轮零工具数据时先分诊待上屏的回答：没有事实断言（寒暄、职责边界、只说明未给出可核对取值）就原样放行。有事实断言才作废并回灌两条路径（去取数 / 本就不需要数据则如实回答，由模型判定）。纠正用尽仍有事实断言 → 受约束的诚实兜底；该调用失败才换确定性文案。定时任务只在这句确定性文案上才换 [NO_DATA] 协议行。
加强收束后还有一层事后核验（GROUNDING_VERIFY，CoV 最小版）：补齐一部分数据后仍可能残留超出证据的断言，这层再核一次；GROUNDING_VERIFY_VOTES>1 时多票裁决，降低核验器自身误判。

⑤ 跨轮重复：观察优先于拦截 repeatCallHint()

跨轮出现同签名调用时不硬拦，只回灌一条观察提示（第几轮已执行过、若确实需要请换参数或说明为何重复）；硬拦会误伤「用户就是要再查一次」这类合法意图。与 ① 是互补的两层：同轮去重管无信息量的并行重复，跨轮只提示。

⑥ 预算耗尽也要有结论 wrapUpWith()

交互式对话打满 MAX_TOOL_ROUNDS 后，各轮过程叙述会被拼成半截话（实测停在「重新写入：」这种悬空半句）。这里用同模型、无工具、非流式再调一次，把「用户原始请求 + 过程记录尾部 WRAP_UP_NARRATION_CHARS」交给它产出收束结论；停在半截动作上要如实交代「未完成」。
两层与无人值守任务的预防式 forceWrapUp 互补，共同保证「预算总有结论」。

知识点（对齐业界）：去重、熔断、卸载、接地护栏对应 Cursor / Claude Code 的 dedup + doom loop + context offload + no-evidence guard。重复调用优先给模型看见，而不是按业务词硬拦。
分页是例外：跨页计数是传输问题，不是推理问题（模型在上下文里逐页累加，准确率极低）。所以客户端硬拦直接翻页（Anthropic programmatic tool calling：allowed_callers 只是引导），由 count_list_by_time 在服务端翻完。这道闸门只看页码字段，不写业务正则。

分页列表：计数在服务端做完

接口只返回分页明细、又要按小时判断有没有超过阈值时，不能让模型当翻页器。每一页明细进上下文再累加，跨页状态会丢（公开测量里这种 inline 计数准确率约 0–7%）。把肥 JSON 卸到工作区文件也解决不了「谁来翻下一页」。子代理独立上下文、轮次只有 10，适合探结构，不适合翻一百多页。

对齐 Anthropic programmatic tool calling：一串工具往返收成一次调用，循环留在 harness 或代码里，模型只看聚合结果。提示词里的 allowed_callers 只是引导，客户端仍要硬拦直接翻页。

翻页闸门 list-page-gate.ts

  • 只认页码形状，不认工具名，也不认业务词：index / offset / skip 的正整数、page 大于 1、非空的不透明游标。布尔 skip、page: "home"、当时间筛选用的 after 不算页码。
  • 离开第一页直接拒绝。每个列表工具本轮只放行一次第一页；换时间窗口或筛选再取一页也拒绝，避免用切片代替翻页。占位在 await 之前，同一批并发请求里只有第一页能通过。
  • 按 id 取详情不拦。第一页调用失败会放开占位，同一参数可以再试。响应还标明有下一页时，即使这次没带页码，也会占住这个工具。
  • count_list_by_time 和 run_tool_code 不走这道闸门，它们自己在服务端或子进程里翻。

服务端怎么翻 countPagedList

  • 列表数组认 data / items / results / records / rows 等，也可以用 rowsField 指定。元素不是对象则整页失败，不当成空的完整结果。
  • 结束条件认 more_data_available / has_more / hasMore，或响应里的不透明 next_cursor。链接和路径形式的 next 不写进请求的 cursor。
  • 下一页沿用 payload 里已经在用的 index / offset / page / 游标，写在 query_params、pagination、paging 或 params，否则写在顶层。
  • 时间字段支持 Unix 毫秒、秒和 ISO，也支持点路径（如 visitor.created_at）。小时桶用 IANA 时区；个别 ICU 把午夜印成「24 点」时进位到下一天 00:00。above 是严格大于。
  • 缺 id、缺可用时间、翻到页数上限、游标不前进、空页却仍标记有下一页：complete: false。这时不回 unique、区间和各小时计数，避免被引用成「没有超过阈值」。接口失败且一行都没入账才是 ok: false；有行但不完整仍是 ok: true，否则接地护栏会把如实说明换成零证据兜底。
  • 页大小被接口拒绝时只减半重试一次。rate limit 不走这条。默认最多 250 页，硬顶 400。通用单页 100 条（环境变量可调，上限 500）。
  • 已知接口适配只留两处，不写进别的工具：Zoho getConversationsList 单页最多 99；没写排序时补 sort_by=in_time、sort_order=asc（offset 翻页没有稳定顺序会漏行或重复）。
  • 完整且有小时桶时，工作区落 results/hour-counts-*.tsv，文件头是 # complete: true。

两条都登记为 read / external：子代理可以调用；只读失败后仍允许换模型重跑。系统提示第 13 条、子代理提示、技能 business-data-query 第 4 步、预警指引 SCHEDULE_ALERT_GUIDE 说的是同一件事，因为这几处读者互相看不见。

12 · 上下文工程

静态 / 动态分离（Prompt Cache）

静态引导（工具调用纪律、角色规则、技能索引、行为准则）拼成 staticGuide，作为 system 首条消息；动态提示（重试、观察、纠正）以 user 消息追加。
收益同一请求多轮循环 system 前缀完全一致 → 命中端点前缀缓存，省 token 且提速。
注意system 消息权重高于 user，语义等价但约束更强。

历史压缩 history.ts

  1. prune（零模型调用）：markdown 表格超 12 行折叠为占位；单条超 3000 字符保头 500 / 尾 300
  2. 仍超预算才 LLM 摘要（≤800 字，要求保留任务目标 / 已确认模块接口 / 数据规模 / 未解决问题）
  3. 摘要结果缓存进会话（historyCompact），跨轮复用不重复摘要；保留最近 HISTORY_MAX_TURNS=8 轮原文（字符预算另有 HISTORY_CHAR_BUDGET）

工具选择策略 TOOL_SEARCH_MODE

auto：工具定义超过窗口 10% 就切 deferred。本轮问题点名或命中的工具预载最多 5 份参数说明，其余再 search_tools；模型直接调用已知但未预载的工具时补上说明并执行。
红线必须保持 auto，改成 off 会让所有角色永远 eager 注入，改变通用大模型行为。movie 角色的 eager 走 per-role 的 forceEagerTools，不污染通用角色。

两段式系统提示

稳定段（角色人设 / 工具纪律 / 环境约定）在前，volatile 段（可用工具清单、当前时间、数据源状态）在后 → 前缀稳定可缓存；AGENT_GUIDE 可整体替换引导词（models.ts:7-11）。

用量透明 usage 事件

把「历史条数 / token / 预算 / 丢弃条数 / 被清理的工具结果数 / 各类重试与熔断计数」回给前端。用户看不见护栏，但排查者必须看得见。

补位收尾的缓存细节 WRAP_UP_HINT

收尾调用复用同一系统提示的稳定前缀（WRAP_UP_HINT），不额外污染 prompt cache。
机制见 §7 ⑥，实践对照见 §23「预算耗尽必有结论」——此处只记这一个与上下文工程相关的增量。

分页明细不进上下文

肥列表先压成短标量（嵌套字段保留点路径，如 visitor.country_code）。跨页计数不把每一页回灌给模型，只回 count_list_by_time 的计数，或 run_tool_code 打印出的聚合。还有下一页时，提示写在结果头部，避免被 12KB 截断切掉。
机制见 §7「分页列表」。卸载到文件解决不了「谁来翻页」。

重复行为的两层分工

跨轮同签名只回灌 repeatCallHint()，不阻断执行；真正的硬护栏是同轮去重与跨轮 Doom Loop 熔断。
机制见 §7 ⑤，对照见 §23「重复行为：反馈 > 硬拦」。
为什么上下文工程的取向是让模型看见自己的行为，而不是替它做决定。

历史坑：曾经在护栏里塞过「问候句式 / 功能词 / 中文参数键」的正则来识别闲聊与伪调用，结果把模型的自由发挥空间压死。现在的纪律是：服务端只做协议形态判断（工具调用写成文本），语义判定（业务 vs 闲聊 vs 意图）100% 交模型。分页是另一件事：闸门只看页码字段有没有离开第一页，不判断「这次查询像不像翻页」。

23 · 知识点清单（点卡片看最佳实践对比）

每张卡片都可点击（或聚焦后回车）打开弹窗，内含业界常见做法 → 本项目做法 → 是否最佳实践 → 偏离原因 → 何时改回去五段对比。✅ 最佳实践⚠️ 有意偏离🐞 已知缺陷

执行 / 推送解耦✅

后台任务 + 事件缓冲，HTTP 连接只是订阅者

业界常见做法
早期很多实现把 req.signal 透传给生成器，连接断开即中止生成。新一代 Agent 服务（含 OpenAI Responses 的 background 模式）把「任务」做成一等公民，连接只是订阅者。
本项目做法
chat-tasks.ts 维护 RunningTask（事件缓冲 + AbortController），后台消费者驱动 chatStream；SSE 连接只转发；收束结果写回会话。
判定
✅ 与最佳实践一致。
为什么重要
用户刷新页面不会丢失结果；断线可续传；同会话重连不会开出第二个任务交错写消息。
何时改回去
无需改。若要跨进程水平扩展，把任务状态从内存 Map 换成外部存储即可，现接口不用动。
事件 seq 游标续传✅

任务内单调 seq，支持按游标补发

业界常见做法
SSE 的 id: + 重连 Last-Event-ID；OpenAI Responses 流式事件的 sequence_number。两者本质相同：给事件编号以便断点续取。
本项目做法
事件信封带任务内单调 seq，GET /chat/task/events?from=<seq> 补齐未收事件；taskId 防跨任务串流。
判定
✅ 与最佳实践一致，且两种业界口径都对齐了。
为什么重要
网络抖动是常态而非异常，续传把「重连 = 重问一次」变成「重连 = 接着看」。
何时改回去
无需改。
Prompt Cache 静态前缀✅

静态引导放 system 首位，动态提示走 user 追加

业界常见做法
把稳定内容（系统指令、工具纪律）放在提示最前并保持逐字节不变，这样多轮之间前缀可命中缓存（Anthropic cache_control / OpenAI 前缀自动缓存）。
本项目做法
staticGuide（工具调用纪律、规则、技能索引）作为 system 首条；重试/观察/纠正等动态提示以 user 消息追加，不污染前缀。
判定
✅ 与最佳实践一致。
为什么重要
工具循环里同一请求会调模型 N 次，前缀稳定才能重复利用缓存，直接省 token 与延迟。
何时改回去
无需改。注意：别把「当前时间」这类每轮变化的内容塞进静态段。
上下文卸载 offload✅

大结果写工作区文件，模型按需 fs_read 取回

业界常见做法
Claude Code / Cursor 把大工具结果卸载到虚拟文件系统，只在上下文里留摘要与路径，模型需要时再读。
本项目做法
offloadToolResult() 写 results/<callId>_<tool>.txt；另一条更早的结果是占位化（TOOL_RESULT_CLEARED）。
判定
✅ 与最佳实践一致。
为什么重要
「截断」会丢信息，「卸载」不丢——只是换个地方，且 usage 事件会显示被卸载条数，行为可见。
何时改回去
无需改。
历史压缩分层✅

prune（零成本）→ 必要时 LLM 摘要 → 缓存复用

业界常见做法
Cursor /summarize、Claude Code /compact：先把低价值内容（长表格、重复代码块）折叠/截断，仍超预算才做一次摘要。用户可见历史 ≠ 模型实际 token。
本项目做法
pruneHistoryTurns（表格超行折叠、长文本保头尾，零模型调用）→ 仍超才 summarizeHistory；结果缓存进会话，HISTORY_MAX_TURNS=8 保留最近原文。
判定
✅ 与最佳实践一致。
为什么重要
直接全量摘要既费钱又丢细节；先 prune 能把「必须总结」的触发点显著推后。
何时改回去
无需改。
去重 + Doom Loop 熔断✅

同轮去重管重复，跨轮熔断管死循环

业界常见做法
把「完全相同的调用」视为无信息量行为并合并/拒绝；对跨轮重复签到-like 行为设阈值熔断（「doom loop」一词即来自此）。
本项目做法
签名只用 name|argsJson：同轮相同只执行第一个；跨轮累积到 DOOM_LOOP_MAX_ROUNDS=3 强制收束。
判定
✅ 与最佳实践一致。
为什么重要
签名不含语义，所以 page 1 和 page 2 不会被去重或熔断当成同一次调用。
和翻页闸门的分工
递增翻页不由去重处理。list-page-gate.ts 另拦：每个列表工具一轮只放行第一页，换筛选再取也拒绝。计数用 count_list_by_time。不要把页码判断塞进去重签名。
何时改回去
去重保持纯签名。若翻页闸门开始拦截按 id 取详情，改闸门的页码判定，而不是把「看起来像分页」写回去重里。
接地护栏 grounding✅

零证据的结论作废 + 回灌纠正 + 诚实兜底

业界常见做法
检索增强场景要求答案可溯源；无证据应降级为「不知道」，而不是生成合理数字。Agent 领域把这条叫 anti-hallucination guard。
本项目做法
grounding.ts：本轮零工具数据却产出结论 → 作废文本 + 回灌纠正提示（给模型两条路径：去取数 / 本就不需要数据则如实回答，由模型判定）；用尽仍无数据则走受约束兜底，禁止事实性断言。count_list_by_time 与 run_tool_code 算外部证据；ok: false 不算。有行但不完整仍是 ok: true，避免如实说明「没数完」被换成零证据兜底。
判定
✅ 与最佳实践一致，且比「硬性要求必须调工具」更灵活（允许模型判断本题本就不需要数据）。
为什么重要
Agent 最贵的错误不是报错，而是「看起来很合理的假数据」。
事后核验（加强）
补齐部分数据后仍可能残留超出证据的断言，因此收束后再走一层 GROUNDING_VERIFY（Chain-of-Verification 最小版）：把证据裁到 GROUNDING_EVIDENCE_CHARS 内交核验器，发现越界断言即作废；GROUNDING_VERIFY_VOTES>1 时多票裁决，避免核验器自身误判把正确答案废掉。
可观测
护栏埋点（groundingRetries / groundingVerifications / ungrounded）写进 run 级 trace，scripts/inspect-grounding.mjs 聚合出 ungroundedRate / retryRate / verifyRate——用于判断护栏是在生效还是在退化。
何时改回去
无需改。若核验延迟明显，先调 GROUNDING_EVIDENCE_CHARS 或关 GROUNDING_VERIFY，而不是放宽「无证据即作废」这条底线。
协议护栏 vs 语义判定✅

只拦「工具调用写成文本」，意图判定交模型

业界常见做法
Cursor 的 <tool_calling> 约束是「必须走工具通道、禁止用文本模拟工具调用」，但没有「查询类不许反问」这类语义条款。
本项目做法
服务端只识别 JSON/XML/方括号/action 形态的伪调用；业务 vs 闲聊、意图、是否反问全部由模型决定，禁止写死词形正则。
判定
✅ 与最佳实践一致（且踩过反面：早期写过「问候句式/功能词」正则，把模型空间压死）。
为什么重要
护栏塞业务正则 → 每加一个业务场景就要改一次代码，且永远追不上。
何时改回去
不需要。若将来想更严格，正确手段是改提示词，不是加正则。
Deferred 工具检索⚠️ 有坑

工具过多时预载少量相关 schema，其余再检索（TOOL_SEARCH_MODE=auto）

业界常见做法
工具数量爆炸时按需加载，并保留 3～5 个与当前问题相关的工具不延迟；模型直接点名时补上 schema 再执行，而不是拒绝。
本项目做法
工具定义超窗口比例（TOOL_SEARCH_RATIO=0.1）才切 deferred，并预载最多 5 个；TOOL_SEARCH_MODE 必须保持 auto。一次工具都没调用却声称取不到，接地分诊判为还没取数。
判定
⚠️ movie 仍单独全量注入：21 个工具、弱模型不会主动检索时会凭记忆编造。
偏离说明
movie 走 per-role forceEagerTools，不把全局改成 off。TOOL_SEARCH_MODE=off 是红线。281 个 Zoho 工具不全量注入。
何时改回去
当主用模型足够可靠地会主动 search_tools 时，可取消 movie 的 per-role 例外。
子代理上下文隔离✅

独立上下文 + 最小工具集 + 结果裁剪

业界常见做法
Deep Agents 的 subagent：把「探查大量原始结构」的工作隔离出去，只把结论带回主上下文。
本项目做法
task 工具派生子代理：独立上下文、最小工具集、结果裁剪到 4000 字符、并行上限 3、可单独取消。轮次上限 10，不拿来翻页；跨页计数用 count_list_by_time。
判定
✅ 与最佳实践一致。子代理是同一次运行里的上下文隔离，不是分页传输，也不是常驻多进程集群。
为什么重要
避免把一次性探索的原始结构永久占用主上下文。用子代理逐页拉列表，轮次不够，而且会把明细又灌回主对话。
何时改回去
无需改。不要靠加大 SUBAGENT_MAX_ROUNDS 来翻完一个长列表。
分页是传输，不是推理✅

服务端翻完页，模型只拿计数

业界常见做法
大结果卸载解决不了跨页累加。Anthropic programmatic tool calling 把一串工具往返收成一次调用，循环留在代码里；并写明 allowed_callers 只是引导，客户端仍要拦住直接调用。Truto 一类做法是整库统计走 spool，不让模型在「下一页」上循环。
本项目做法
确认字段：每个列表工具一轮只直接取第一页。count_list_by_time 按小时翻完，complete: false 不回各小时数字。run_tool_code 做其它汇总，明细不出子进程。list-page-gate.ts 硬拦第二页和换筛选再取。只认页码字段。
判定
✅ 与上述做法一致。Zoho 会话列表另有两处接口限制（单页 99、缺省 in_time 升序），不写进其它工具。
为什么重要
模型在上下文里逐页累加，公开测量准确率约 0–7%。半截扫描若还带回峰值，会被说成「没有超过阈值」。
何时改回去
不要把页码判断并进去重或熔断。若闸门拦了按 id 取详情，收紧页码判定，而不是放行直接翻页。
Fail-closed 写确认✅

一次性票据 + 会话绑定 + 超时即拒

业界常见做法
写操作二次确认，默认保守；凭证不可重放；超时按拒绝处理（fail-closed）。
本项目做法
ticket 一次性且与会话绑定；必须先注册 waiter 再发事件（否则前端秒确认会失败）；未声明风险级别的工具一律需确认；批准/拒绝/超时都落审计。
判定
✅ 与最佳实践一致。
为什么重要
宁可让用户多点一次，也不要「点了拒绝却执行了」。
何时改回去
无需改。
不可信内容围栏✅

nonce 围栏 + 伪造标签中和 + 控制字符剥离

业界常见做法
把第三方文本（网页、检索结果、上传文档）标记为不可信输入，并用随机分隔符防止内容伪造边界；必要时限制模型把它当作指令。
本项目做法

何时改回去
无需改。
诚实失败 > 坏交付✅

条件不满足就报错引导，不产出看起来正常的坏文件

业界常见做法
Fail fast / fail loud：不可用时明确失败，而不是降级成一个「看起来成功」的结果。

PDF 缺中文字体 → 如实报错并建议改用 docx/html（否则中文全白）；成本统计未配单价 → 只计 token 并计入 unpricedTokens，不编造金额；embedding 不可用 → 降级纯词法不报错（这条属于能力降级，已明示）。
判定
✅ 与最佳实践一致。
为什么重要
坏产物会被下游采用，排查成本远高于一次报错。
何时改回去
无需改。

无需改。

重复行为：反馈 > 硬拦✅

跨轮同签名只回灌观察提示，裁决权留给模型

业界常见做法
只合并/拒绝完全相同的调用（同轮去重）。跨轮重复业界一般不做硬拦——因为「用户就是要再查一次」是合法意图。
本项目做法
executedSigRounds 记录签名首次执行的轮次，跨轮再出现时回灌 repeatCallHint()（第几轮已执行过、确实需要请换参数或说明理由），不阻断执行；同轮去重与跨轮 Doom Loop 熔断仍是硬护栏。
判定
✅ 与最佳实践一致（对齐 Anthropic 上下文工程的「让模型看见自己的行为」）。
为什么重要
硬拦会误伤合法重查；给反馈既保留信息，又把决定权交给看得见上下文的一方。
何时改回去
无需改。注意别把「观察提示」升级成拦截——那就退回误伤。
预算耗尽必有结论✅

打满轮次后同模型补一次收尾，不留半截话

业界常见做法
长任务要么提前总结（预防式），要么在退出路径上做一次收束；任何退出路径都必须产出可用结论是 Anthropic 上下文工程的明确建议。
本项目做法

25 · 红线与工程纪律

① 「全部由大模型判断」

服务端不做语义正则预判：问候句式、功能词、中文参数键、JSON 字段名功能词都不许写死。
允许：协议结构护栏、数量/循环护栏、HTTP 方法、英文 CRUD 契约词、通用字典（id→ID）。

② 禁止业务词写死

代码逻辑/正则/映射表/配置/工具描述/错误提示/示例一律不许出现具体业务词，示例用 XX / <模块> / <接口> 占位。
豁免：mock 与「实时扫源码」的特例，严格隔离。

③ MCP / 数据库只读

BI 库不执行任何写 SQL；不改任何 MCP 服务器配置、工具清单、凭据。只读查询、列元数据、取值域是可以的。

④ 「删」≠「去掉显示」

用户说「去掉」「别显示」时，指的是隐藏展示（如在技能面板不列出），绝不删功能文件。索引、加载路径、校验白名单保留全量。

⑤ 提交纪律

改动完成后先给用户看，不自动 commit / push；只在用户明确要求时才提交。

⑥ 诚实优先

查不到就如实说查不到，不用训练记忆或其他域数据补全；额度/限流失败如实降级；未配置的能力如实说不可用。
