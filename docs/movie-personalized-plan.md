## 0. 实施前探测结论（重要，已改变设计）

对豆瓣 MCP 做了协议级探测（`search_movie` / `get_movie` / `get_movie_chart`）：

| 探测项 | 结果 |
|---|---|
| `search_movie` | 入参 `{q(必填), count 1–20}`；返回 **markdown**（`1. **片名 年份** ⭐评分` + `🔗 https://movie.douban.com/subject/<id>/`）。**无类型/关键词字段** |
| `get_movie_chart` | 入参 `{kind: top250\|weekly\|new, start, count 1–25}`；markdown；**`new` 榜无评分** |
| `get_movie` | **无 `DOUBAN_COOKIE` 一律被风控**；连续调用会触发「访问限流，请等 1 分钟」 |

**两个设计后果（必须接受或改决策）**：

1. **拿不到类型/关键词** → 「按类型/年代交叉检索」无数据可依。调整为：
   - 候选来源 = ①**标题检索**（`search_movie(q=种子片名)` 会带出系列片/相关片）②**模型推导的口味标签**作为检索词（模型只知道「《星际穿越》→ 科幻/太空」这类**通用题材词**，只用于**构造检索词**，不作为事实陈述）③`get_movie_chart(new/weekly)` 提供新鲜度。
   - 红线说明：口味标签由模型产出而非服务端写死词表（不违反「禁止业务词写死」）；候选仍**全部来自豆瓣返回**。
2. **详情能力当前不可用**（`get_movie` / 短评被风控）→ 「这部片讲什么」「为什么推荐」只能给**片名 / 年份 / 评分**，给不出类型 / 简介 / 演职员。
   - 这是「零凭证」的直接代价，**可接受**（已确认「先用启发式，后续可替换」）。
   - **可选增强**：日后配 `DOUBAN_COOKIE` 即可解锁详情与短评（推荐管线与 UI 无需改动，只是候选与理由变丰富）。
3. **豆瓣有速率限制** → 推荐必须**预计算 + 长 TTL 缓存**（与 §7 的 C1/C3 一致），禁止在「打开页面」时实时打豆瓣。

## 1. 需求拆解

## 1. 需求拆解

用户原话拆成四条：

1. **核心功能**：基于「每位用户的观看历史」，自动推荐**相似电影**。
2. **主动展开展示**：每次用户打开应用时，系统**主动**展示与其**最新观影偏好**相关的**最新影片**推荐。
3. **能力补齐**：主流「观影助手 Agent」有的功能，这里也要有（按网上最佳实践补充）。
4. **流程要求**：先出方案 → 加进文档 → 对齐后再开始。

## 4. 关键决策 A：观看历史从哪来

| 方案 | 怎么拿 | 优点 | 缺口 |
|---|---|---|---|
| **A1 豆瓣账号收藏** | `get_user_collections`（公开 uid 可匿名读；私密/详情需 `DOUBAN_COOKIE`） | 真实、量大、自带评分 | 需你提供 uid（或 cookie）；私密收藏读不到 |
| **A2 应用内累积** | 对话中用户提到的「看过/喜欢/不喜欢」→ 结构化入画像库 | 零凭证、隐私自持、可持续增长 | 冷启动为空，需时间积累 |
| **A3 显式口味校准** | 首次打开让用户挑/评 5 部片（可跳过） | 立刻可用、可控、一次成本 | 一次性打扰 |

**已确认（2026-09-18 修订）**：**只走 A2 —— 从对话中累积**（零凭证）。

- 用户明确否决了 A3 的「挑片校准」表单（原话「不要这个」），因此**前端不再有校准入口**；冷启动改为「展示榜单兜底 + 一句被动提示（聊聊你看过的片，推荐会更准）」。
- **A2 的落地机制**：新增内置工具 `record_watched_movies`，由**模型**在用户明确提到「看过 / 喜欢 / 不喜欢某片」时调用（见 §11.2）。服务端不做任何语义识别（守红线）。
- A1 豆瓣收藏导入本期不做。

## 5. 关键决策 B：「相似」怎么算

| 方案 | 依据 | 成本 / 风险 |
|---|---|---|
| **B1 TMDB `/movie/{id}/similar` + `/recommendations`** | 内容相似（类型/关键词/主创）+ 协同过滤（看了这部的人还看什么），业界标准；支持 `language=zh-CN` | 需 **TMDB API key**（免费申请）；中文片名与豆瓣 id 需映射 |
| **B2 豆瓣启发式（自算）** | 从历史片提取类型/年代/关键词 → `search_movie` 检索 + `movie_chart` 交叉 → 按评分/新鲜度排序 | 零额外凭证；**但不是真「相似」**，准确度低 |
| **B3 抓豆瓣「喜欢这部电影的人也喜欢」** | 豆瓣自己的相似推荐，最贴中文用户口味 | 豆瓣 MCP **没有这个工具**，需自写抓取（风控风险、违背「不自己造数据源」的初衷） |

**已确认**：本期走 **B2 豆瓣启发式**（零额外凭证）；B1 TMDB 列为**后续可替换的升级项**（接口形状预留）；B3 不做。

**B2 的实际做法**（受 §0 探测结论约束——豆瓣不返回类型字段）：

1. **标题检索**：`search_movie(q=种子片名)` → 带出系列片 / 同名相关片（实测「星际穿越」→「星际穿越2：虫洞」「走进《星际穿越》」）。
2. **模型推导检索词**：把用户喜欢/看过的片名交给模型，产出**通用题材词**（如 太空 / 硬科幻 / 悬疑），**仅用于构造 `search_movie` 的 q**；服务端不写死任何题材词表（守红线），也不把标签当事实断言。
3. **榜单新鲜度**：`get_movie_chart(new / weekly)` 提供「最新影片」来源（呼应「最新观影偏好相关的最新影片」）。
4. 合并去重 → 过滤已看 / 已忽略 / 种子自身 → 排序（评分 × 新鲜度 × 题材命中）→ 理由「因为你看过《X》」。

> 说明：TMDB 若日后接入，只替换「候选生成」这一步；片名/评分等**展示数据仍以豆瓣为准**，避免双源数字打架。

## 6. 推荐管线（服务端确定性流程，不依赖 LLM 出候选）

```
画像(历史 + 反馈 + 已看 + 想看)
  → 种子选取：最近 N 部高偏好（明确 like / 有评分 / 最近加入的历史）
  → 口味标签：模型从种子片名推导通用题材词（只用于构造检索词，词表不落代码）
  → 候选生成：
       ① search_movie(q=种子片名)      → 系列片 / 相关片
       ② search_movie(q=每个口味标签)   → 题材候选
       ③ get_movie_chart(new|weekly)   → 新鲜候选
  → 合并去重（按 subject id）
  → 过滤：种子自身 / 已看 / 已忽略 / 无评分且非最新
  → 排序：评分 × 新鲜度 × 题材命中 × 多样性（同系列限 1 条）
  → 解释：每条附「因为你看过《X》」或「与你偏好的<标签>相关」
  → 缓存：写回画像（偏好指纹 + TTL 12h）
```

**为什么不让 LLM 直接生成候选**：候选必须可追溯到豆瓣返回，避免编造片名（现有观影 skill 的红线）。模型只参与**检索词构造**与**文案**，不参与候选实体生成。

**速率约束**：豆瓣有风控与限流（实测连续调用即触发「等 1 分钟」），因此管线必须**离线预计算**，打开页面时**只读缓存**。

## 7. 关键决策 C：「打开即展示」怎么实现

| 方案 | 做法 | 评价 |
|---|---|---|
| **C1 服务端预计算 + 打开即读缓存（推荐）** | 触发时机：①画像变化 ②TTL 到期（默认 12h）③每日定时（`schedules.ts`）。前端 `MoviePage` 顶部渲染「为你推荐」卡片区，**不进对话历史** | 打开 ≤1s 出内容；零 token 成本；可解释可控 |
| C2 Agent 主动发消息 | 打开时自动给模型一个隐藏提示，让它查完再写成对话 | 每次打开都跑模型 30–160s + 花钱；「打开即展示」体验不达标 |
| C3 混合 | C1 出卡片；卡片上「让助手聊聊这部」再交给 Agent 做对话深化 | **推荐**：静态秒出 + 需要时对话 |

**已确认 C3**。卡片动作：`加入想看` / `不感兴趣` / `让助手聊聊这部`（后者把片名与来源交给 Agent 做对话深化）。

## 9. 与现有红线的契合

- 推荐管线是「取数 + 过滤 + 排序」的确定性代码，**不写死任何业务词**（类型/关键词来自数据与画像）；不用业务正则做语义判断。
- 文案：卡片理由可用通用模板（`因为你喜欢《{title}》`），对话内的解释由模型生成。
- 一切按 `ownerKey` 隔离；反馈/画像写入走审计；不引入新 MCP 之外的爬虫（B3 若要做单独立项）。
- 复用既有基建，不新增同类机制（schedules / chat-tasks / memory / Mongo 集合模式）。

## 10. 验收标准

1. **空画像新用户**：打开看到口味校准（可跳过）+ 榜单兜底，不空白。
2. **有画像用户**：打开 ≤1s 出推荐卡片（缓存命中）；重算路径 ≤5s。
3. **不出现已看/已忽略**的片。
4. 每条推荐带可追溯理由（引用具体种子片）。
5. **新鲜性**：推荐集中至少有 1/3 是近 2 年或近期上映片。
6. 跨用户不串（ownerKey 隔离用例）。
7. 「不感兴趣」后刷新不再出现该片（反馈生效可验证）。
8. 成本可控：打开页面不触发模型调用（C3 下）。

## 11. 已确认决策

| 决策 | 选择 |
|---|---|
| 观看历史来源 | **A3 口味校准 + A2 应用内累积**（零豆瓣凭证；A1 收藏导入不做） |
| 相似度算法 | **B2 豆瓣启发式**（标题检索 + 模型推导检索词 + 榜单新鲜度；B1 TMDB 预留可替换） |
| 打开即展示 | **C3 卡片区 + 助手深化**（服务端预计算缓存，打开只读缓存，零 token） |
| 清单 / 提醒 | **只做想看清单**；定时提醒**本期不做** |
| 已知降级 | 无 cookie ⇒ 详情/短评不可用 ⇒ 卡片只能给 片名 / 年份 / 评分，无法给类型 / 简介 |

```
tags=["科幻","悬疑","烧脑","高概念"]  items=12（服务端零词表，由模型推导）
  - 走进《星际穿越》⭐9.4         :: 因为你看过《星际穿越》
  - 盗梦空间：行动开始 ⭐9.2       :: 因为你看过《盗梦空间》
  - 詹姆斯·卡梅隆的科幻故事 ⭐9.1 :: 与你提到的「科幻」相关
  - 看不见的客人 ⭐8.8           :: 与你提到的「烧脑」相关
  - 东方新科幻 (2024)            :: 与你提到的「科幻」相关
  - 记忆碎片 ⭐8.7               :: 与你提到的「烧脑」相关
```

- 冷启动（空画像）：12 条榜单兜底 + `needsCalibration=true`（前端据此引导校准）。
- 缓存命中：二次调用 `cached=true` 且 `computedAt` 不变（**不再打豆瓣**）。
- 反馈生效：标记已看后重算，该片被排除。
- 多样性：同一部种子片最多贡献 1 条（实测把同一部片的 3 条衍生内容压到 1 条）。

**验证注意（踩过的坑）**：

1. **豆瓣对高频很敏感**：连续跑多套验证（每套都会触发真实重算）会触发风控/限流，此时对话会**如实回复「拿不到数据」而不是编造**（实测如此，属预期行为）。跑验证请**串行并留间隔**。
2. **调用 MCP 的自检脚本必须显式 `process.exit()`**：MCP stdio 连接会让事件循环保持存活，否则脚本打印完不退出，留下挂住的进程与豆瓣子进程（本次踩到，已修 `_movie-e2e.mjs` / `_movie-recs-check.ts` / `_movie-api-check.mjs`）。
3. 端点已按 owner 限流（推荐 12/分、搜索 20/分，可用 `RATE_LIMIT_MOVIE_*` 调整），防被刷导致豆瓣封禁。

## 11.2 A2 的落地机制（模型驱动的口味记录）

- **工具**：内置 `record_watched_movies`（英文契约名），入参 `movies[]`（`title` 必填，`id`/`year`/`rating`/`verdict` 可选）。
- **风险级别**：`write` + `scope: "workspace"` → 按 `risk.ts` 的 `verdictNeedsConfirm`（`external && level !== read`）**免二次确认**，因为它只写本机画像、无外部副作用。
- **owner 隔离**：`ownerKey` 从 `chatStream` 的 opts 一路透传到循环上下文与 `execBuiltin`（不暴露给模型），子代理继承同一 ownerKey。
- **服务端零语义判断**：何时调用完全由模型按 skill 判断（「用户明确表达观影经历或偏好时才记录；不要把助手的推荐当成用户看过」）。
- **实测**：用户说「我看过《星际穿越》和《盗梦空间》，特别喜欢第一部，不太喜欢《变形金刚》」→ 模型先 3 次 `search_movie` 拿信息 → 调 `record_watched_movies` → 画像落库 `history=3`、`星际穿越:like`、`变形金刚:dislike`，并自行推断出「偏爱诺兰式科幻」。

> 已知简化：内置工具目前**按角色过滤**（`builtinToolSpecs` 全局注入），所以 `record_watched_movies` 对通用助手同样可见。实践中这不算问题（用户在 `/chat` 聊到影片时也会顺手记录口味，而画像只被观影页消费），但若将来要让工具按角色收窄，需要给 `builtinToolSpecs` 增加角色参数。

## 11.3 片源不可用时的降级契约（重要）

豆瓣对匿名高频访问会风控/限流（实测：连续验证流量后，连 `search_movie` 都返回「触发风控」，持续数分钟以上）。因此：

| 场景 | 行为 |
|---|---|
| 重算拿不到候选，但有旧推荐 | **保留旧推荐**并返回 `stale: true`（前端提示「暂时拿不到新的推荐，先看上一次的结果」） |
| 重算拿不到候选，且无旧推荐 | 返回空 + `stale: true`，**不写缓存**（否则空结果会粘住整个 TTL 且不再重算） |
| 连续 2 次调用无结果 | **提前止损**，不再把剩下 7 次打完（避免加剧对方限流） |
| 防抖窗口内 | 复用**最近一次返回的结果**（含空结果），不依赖落盘缓存，避免客户端重试持续打豆瓣 |
| 对话侧 | 模型按 skill 守则**如实说明拿不到数据**，绝不凭记忆编造（实测如此） |

> **运维建议**：匿名访问随时可能被风控。要稳定使用请配置 `DOUBAN_COOKIE`（`.env` 已留注释占位）——既大幅降低风控概率，也能解锁详情/短评。

### 已知质量局限（与决策一致）

- 标题检索会带出**制作特辑 / 同名衍生片**（如「走进《星际穿越》」），这是 B2 启发式的固有弱点；已用多样性约束压制，但仍不如 TMDB 的 `similar/recommendations`。
- 无 cookie 时**没有类型/简介**，因此题材词只能由模型从片名推导（质量取决于模型），卡片也给不出一句话简介。
- 升级路径不变：接入 TMDB 只替换「候选生成」一步（见 §5）。

## 12. 不做什么（边界）

- 不做在线播放 / 购票 / 版权跳转。
- 不做 LLM 端到端生成候选（幻觉风险，候选必须来自数据源）。
- 不做自建爬虫抓豆瓣页面（除非你明确要 B3 并接受风控风险）。
- 不改现有 `/chat` 通用助手形态。
