# 陌生库探查流程

适用场景：第一次接触某个库 / 表，或字段语义、表关系、主键口径不确定时。
典型征兆：想靠字段名猜语义；想「先关联维表再说」；想「看着像脏数据就顺手排掉」。

## 步骤

1. **先找存量口径，再自己写**：用元数据 / 搜索类工具找同一口径的既有定义（已保存的查询、仪表盘、SQL）。有现成的就以它为基准，不要重新发明一遍。
2. **字段语义不确定 → 先取取值域**：
   - 用取值分布工具（如 BI 适配器的 `get_field_values`；没有该工具时用最小聚合查询）看：真实去重值有哪些、各自出现次数、是否存在空串或 NULL、是否存在「默认值」成员。
   - **取值域里出现的值就是真实存在的取值**，不能因为「看起来像脏数据 / 异常」就把它过滤掉；要排除必须给出业务理由并写明口径。
3. **读元数据而不是猜**：表 / 字段的描述、语义类型、外键指向能直接回答问题；描述缺失时以数据（取值域 / 样本行）为准，并说明「依据取自数据而非文档」。
4. **表关系不确定 → 先用单表口径**：关联会额外引入假设（连接键唯一性、维表基数、空值匹配）。先跑单表口径，再跑关联口径，两者不一致时查清差在哪，不要默认关联后的结果才对。
5. **主键 / 唯一性不靠命名猜**：用总数与去重数（`count(*)` vs `count(distinct …)`）验证候选键；叫 `id` 的列未必是业务主键。
6. **结论写清口径**：用了哪张表、哪些过滤条件、为什么保留或排除某个取值；不确定的部分明说不确定，不要用「数据看起来不对」收尾。

## 注意

- 每次取证都用最小代价：加 `LIMIT`、只取一列、先花一轮把假设证伪，比写完长查询再返工便宜得多。
- 结构探查结果很大时，可委派子代理专门做「探 schema」这一步，只把结论带回来，避免把大量原始结构灌进主上下文。
- 本流程只决定「怎么取证」，不替业务下结论：业务口径仍以用户或既有定义为准，用户明确说了口径就按用户说的执行。
