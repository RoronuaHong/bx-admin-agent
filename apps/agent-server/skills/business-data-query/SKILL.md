# 业务取数流程

适用场景：用户要一个属于已连接自有业务数据的数字。这是本助手最高频的任务，也是最容易出错的一类：**数字看起来合理就没人会去核对**，所以错口径会被直接带进决策。主体落在外部世界时不要进入本流程，也不要用本流程去验证那个主体是不是自有数据。

流程固定为「先确定问的是什么 → 找存量口径 → 取证 → 取数 → 核对 → 交付」。每一步都有明确的产出，跳过任何一步都可能让后面白做。

## 步骤

1. **先确定问的是什么**：把口径写成三个问题——时间范围（哪天到哪天）、粒度（按天 / 按渠道 / 按用户）、过滤条件（哪条业务线、哪些状态）。三者都会改变结果。口径不唯一时按系统提示第 8 条：检索能把读法分开就先查，分不开再问，不要自己挑一个更常见的。
2. **先找存量口径；有就**直接执行**，不要照着重写**：用搜索 / 列表类工具找同一口径的既有定义（已保存的提问、仪表盘、卡片）。**找到就直接执行那个提问来取数，不要只读它的定义、然后自己重写一遍 SQL**——重写既慢，又更容易把口径走偏。同一个指标出现两套算法，比数字本身错更难排查。指标定义互相冲突时，改走「指标口径核对」。
3. **确定没有现成口径才自己写查询**：这时才写新 SQL；写之前先用「构造查询」类工具确认它是只读且能跑通，再执行——**先确认口径再执行，不要用「边写边试」消耗轮次**。写跨表 JOIN / 聚合前，先用 `search_columns` 扫一遍全集群列，确认哪些表真的有你要的关联列——不要凭一张表的字段名就猜别的表也有同名列，也不要因为一张表里没看到就断定整个库没有。
4. **陌生表先取证**：加载并执行「陌生库探查」，不要在这里另写一套探查步骤。结构很大时，委派子代理只把结论带回来。
5. **查询只读、最小代价**：先用一页确认字段，再在服务端或代码里完成聚合。**大结果不要往回捞**——结果被卸载成文件后，逐个读回来既慢又占预算；正确做法是**重新发一条已经聚合好的查询**（分组、去重、求和），或用代码工具在服务端把明细汇总成几行再看。跨页计数与小时汇总按工具使用纪律执行。
6. **交付前自己核对一遍**：量级对不对（与总量或上次同类结果比）、口径是否就是用户问的那个、有没有 NULL / 空串被静默排除。**逐个子问题过一遍，确认每一个都有交代**——给到数字、或给出数字并说明限制、或明确说缺什么数据，三者选一，不允许漏掉任何一个。
7. **某个维度实在取不到时**：先确认你要的**粒度与时间维度在这个来源里真的存在**（要按天但只有快照、要按主体但该表没有主体列，属于"这个来源给不了"）；**换来源之前，先用 `search_columns` 按列名子串扫全集群，确认这个列在哪些库、哪些表里真的存在**——只有全集群都找不到该列，才是真的"这个来源给不了"，再如实说明。再换一个候选来源试一次（关联表 / 明细表 / 快照表 / 已保存提问）。**换过来源仍然拿不到，就在答案里并列写清试过哪些来源、各自缺什么**——不要说成"库里没有"。注意顺序：**先把能答的部分答完并交付，最后再单独说明哪一部分取不到**；不要让取不到的部分取代整体交付。

## 本连接器已知事实（避免误判）

以下是从本数据源反复踩坑后确认的事实，违反它们会直接给出错误结论，请当作硬性前提：

- **国家/地区维度不在活跃、会员事实表里**：`elt_active_guid`、`elt_user_vip_info`、`elt_user_vip_recharge_log` 等**没有国家/地区列**。用户维表 `elt_user_full` 才有 `countryCode`（电话国家码，如 91=印度、55=巴西）与 `ipCountryCode`。**要按国家拆任何指标，必须按关联键把事实表 JOIN 到 `elt_user_full` 取国家（关联键先 `DESCRIBE` 确认）**，不要因为事实表本身没国家列就写"按国家取不到"。
- **国家维度只认 `elt_user_full.countryCode`，不要用替代列**：库里另有几个"看着像国家"的字段会把口径带偏——`elt_app_params.countryCode` 是**累计设备明细**口径（基数远大于活跃口径、同一设备可多行，拿来算日活会虚高）；`ipCountryCode` / `networkCountryIso` / `localeIso3Country` 是 IP 与网络推断，与账号注册国不一致；`elt_film_user.country` **实测全为空**。按国家拆指标一律走 `elt_user_full.countryCode`（91=印度、55=巴西、92=巴基斯坦、52=墨西哥、880=孟加拉）。
- **会员"退订/流失"先探到期列，再下结论**：不要凭"没看到退订事件表"就断言答不了。先 `DESCRIBE` / `get_database_schema` 看 `elt_user_vip_info` 是否带到期/结束时间列（如 `vipEndTime` / `expireTime`）；若有，可据此定义"到期时间已过且充值日志里无后续续费"的流失人群。只有确认既无到期列、也无任何续费/取消事件流，才写"本源无法直接给出退订人群"。
- **会员存量分两类口径，别混**：
  - **当前存量（查询时刻）**：`elt_user_vip_info` 中 `vipType = 2 AND endDate > now()`，账号去重 `uniqExact(uid)`；`status = 0` 实测不起作用，可不加。会员表**一号一条**（`count() = uniqExact(uid)`），服务账号极少数需排除。
  - **历史存量 / 某基准日 D 的存量**：会员表只保留账号**当前**状态，过去断过又续的会员无法从表里还原，所以**不能**用 `startDate <= D AND endDate >= D` 反推历史——这会漏算"在 D 之前断过、D 之后又开"的人、或把"D 时恰好在期但早已流失"的算进去，算出与真实趋势**相反**的假"回升"。正确做法是用**开通流水重建**：在 D 时刻，账号"D 之前最近一笔开通记录的 `endTime` 晚于 D"即为会员；逐基准日重算后与「新增 − 流失」瀑布交叉验证（见「指标契约」）。
  - **不要**用 `elt_user_full_history.vipExpireDay > 0` 这类设备级快照替代——覆盖不全（整日缺失、只保留近 30 天），早期计数偏低、算反趋势，且设备维度一号多机放大。判断"会员是升是降"必须以两基准日存量对比为准，并用「新增 − 流失」交叉验证（两者应能对上）。
- **"新增会员" ≠ "首次付费（首充）"**：`rechargeType=3 & isFirst=1`（首充）里约 64% 是**断后回流**的老会员（他们本来就是会员，不会让存量增加），首充总数约为"全新会员"的 2.8 倍（早年版写的"5 倍"是错的）。算会员净增时必须拆**流水瀑布**：**新增** = 窗口内第一次成为会员的账号（`uniqExact(uid)`）；**回流** = 期初非会员、期末是、此前开通过；**流失** = 期初是、期末不是。首充只能作为"付费转化"单独口径，**不能拿来抵消流失，也不能与"到期数"直接相减**（首充 = 新开通 + 回流，混用会得出相反结论）。会员表一号一条，`startDate` 无法区分新开通与回流，替代口径同样不可靠——一律走流水瀑布。
- **跨表统计默认去重到账号（用户未指定去重主体时）**：`elt_user_vip_info` **一个账号一条记录**（会员表一号一条，实测印度 `count() = uniqExact(uid)`）；早年版写的"1.6 倍"来自关联设备宽表 `elt_user_full` 的放大，不是会员表本身。`elt_user_full` 是设备级宽表（一号多机）。凡涉及"多少会员 / 多少用户"，聚合必须用 `uniqExact(uid)`；用 `count()` 数记录会系统性虚高。**这条同样适用于「运行代码」（run_tool_code 里的 Python/pandas）：按 uid 去重，勿按 guid（`df['guid'].nunique()` / `len(df.guid.unique())` / `drop_duplicates('guid')` 都会复刻设备级虚高）。代码执行器已对 guid 邻近计数/去重动词给出同源告警，但别依赖它——下笔前就按账号口径写。

- **慎用 `metabase_upload` 等预聚合中间表**：如 `metabase_upload.mid_channel_source_guid` 这类已带 `channel + source` 的中间表，覆盖面常宽于明细口径、且可能只覆盖部分时段（实测同一来源拆分与明细表 `elt_ap_channel` ⋈ `elt_gp_install_referrer_log` 可差数倍、且各来源倍数不一致，说明不是同一口径）。需要来源 / 渠道拆分时优先走明细主表，用之须声明其覆盖时段与口径局限，不要静默当主口径。

## SQL 怎么写

写查询前按这几条来（**都是通用实践，与具体业务无关**）：

1. **结果集要有界**：明细一律加 `LIMIT`；`GROUP BY` 的分组基数由数据决定，也要加 `LIMIT` 并按需 `ORDER BY … DESC` 截断。只要列要用的列，别 `SELECT *`。
2. **别做全表扫描**：明细事实表至少加能裁剪的过滤条件。确实需要全扫（探数据边界）时，在回答里说明这一点。
3. **谓词要可裁剪**：不要在 `WHERE` 里对列套函数（`toDate(col) = …` 会退化成全扫，也把真实范围藏起来了）。时间用裸列范围 `col >= '起' AND col < '止'`（左闭右开）；字符串用 `LIKE '前缀%'` 或 `IN (…)`，别用 `LIKE '%…'`。
4. **分组要完整**：`SELECT` 里的裸列要么进 `GROUP BY`，要么用聚合函数包起来——否则分组后取值是任意的（有的引擎报错，有的**静默给错值**）。
5. **别写出笛卡尔积**：`JOIN` 必须带 `ON`；不要用 `FROM a, b` 这种逗号并列；`ON` 里的表/别名必须是 `FROM`/`JOIN` 里真实声明的，别拼出不存在的表或别名（工具会在执行前提示）。
6. **嵌套别超过 3 层**：改成 `WITH … AS` 分层写。
7. **列式引擎的写法**：`count(DISTINCT x)` 退化为全量去重，用 `uniqExact(x)`（精确）或 `uniq(x)`（近似）。查结构用 `DESCRIBE <table>`，别用 `SHOW CREATE TABLE`（会输出建表细节）。
8. **别把"没跑完的一天"当完整日**：当天（或数据尚未生成完的那天）的活跃/订单计数会明显偏低。**算均值、环比、占比、趋势时必须把这天剔掉**（不能"只标注了却照样放进平均"——那是自相矛盾）；只有当结论本身就是"当天数"时才展示它，并明确标注"数据不完整"。否则会被误读成"断崖下跌"。

示例（通用结构，零业务词；时间用左闭右开裸列范围、分组加 LIMIT、聚合默认用 `uniqExact` 精确去重——**用户给定 `uniq` 近似或指定 `guid` 设备口径时按用户来**、`SELECT` 只列需要的列）：

```sql
SELECT col_dim, uniqExact(col_user) AS cnt
FROM sch.tbl
WHERE col_time >= '起' AND col_time < '止'
GROUP BY col_dim
ORDER BY cnt DESC
LIMIT 100
```

写完不必逐条自查——工具会在执行前把上面这些体检出来告诉你，照着改即可。完整判据与理由见 `docs/agent/BI_HEAVY_QUERY_GUARDRAIL.md`。

## 资源纪律（避免把库打挂）

重聚合查询一旦吃满内存，会拖垮整台数据库、连累同一账号下的其它查询（含业务流量）。这类问题工具**放行但不免责**——执行前会给提示，务必照着改。通用做法（与具体业务无关）：

0. **优先复用现成聚合，不要每次全量重算**：日活、留存、会员存量、漏斗这类指标，生产环境通常有预聚合物化视图（命名常含 `_mv` / `_daily` / `_retention`）或已验证的 Metabase 卡片。先用 `list_cards` / `get_card` 找现成卡片、或确认是否存在预聚合表并优先走它；避免每次用 `uniqExact(uid)` 对全量明细宽表扫几十天——那既慢又易爆库，正是 2026-10-16 事故的根因形态。确需扫明细时再按第 1 条小窗探通。
1. **先小范围探量级，再放大**：第一条查询用 1~3 天窗口跑通、确认量级合理，再逐段放大时间窗。不要一上来就扫几十天。
2. **趋势/看板类优先用近似计数**：`uniq()` 是自适应采样近似，内存占用极低、误差约 1~2% 且量级一致；只有对账/结算这类必须精确的口径才用 `uniqExact()`。**近似与否是口径判断，需用户或场景确认**——不要默认替用户选精确口径，然后一条查询吃满内存把库打挂。
3. **逐 ID 循环取数必须合并成单条**：对同一维度的多个值分别发一条查询（如 `WHERE dim = v1` 连发 N 次），会放大成 N 倍全表扫描；改成一次性 `WHERE dim IN (v1, v2, …)` 或 `GROUP BY dim` 一次取回。
4. **重聚合的代价提示要听**：`uniqExact()`（高基数精确去重）、多表 `JOIN` 且无时间窗、`GROUP BY` 维度 ≥3 且无 `LIMIT`——这些会被工具标记为资源高风险，按提示缩窗 / 改用近似 / 加 `LIMIT` / 先各自过滤再 `JOIN`。

## 交付格式

- 开头一句话给结论 + 口径（数据源 + 时间范围 + 粒度 + 过滤条件 + 生成时间），让用户一眼知道这数怎么来的。
- 第二句给来源：用了哪张表 / 复用了哪个既有定义；若由 agent 自主选表，必须声明所选表及其口径局限（覆盖时段、设备 / 账号口径等）。
- **每个数字 / 表格都带口径标注**：去重主体（guid 设备 / uid 账号）、去重函数（uniq 近似 / uniqExact 精确）、粒度、过滤条件、时间窗，尽量进标题或脚注，不藏在正文里。
- 部分周期 / 数据未同步完的，明确标注「近似值 / 非完整周期」，不混进完整周期的平均或同比。
- 可能影响解读的点如实说明（例如「已排除 status 为空的 3 条」「该分组小基数，变化率不解读」）。
- 用户要图时再出图；要明细时再给明细行。
- **有子问题答不了时**：写清「哪个子问题 + 试过哪些来源 + 每个来源缺什么 + 需要补什么数据才能答」。不允许只写一句"库里没有"就带过。
- 末尾可附一行可复算声明（数值来自本次实时查询、可与明细表交叉验证）。

## 多语言与国际化支持

本数据源大量指标带语言 / 地区维度（如印度多语言内容 `contentLang`、国家码 `countryCode`）。处理多语言场景时：

- **语言维度有两套口径时，必须显式声明用哪套，不要二选一卡住**：例如内容语言 `contentLang`（常见取值 `''`=英语、`te-IN`=泰卢固语、`ta-IN`=泰米尔语、`ml-IN`=马拉雅拉姆语）与音轨语言（Hindi / English / Tamil / Telugu / Malayalam / Default-OST / Other）是**两套不同口径**，结果不互通。用户未指定时，选一套最贴近可得口径先算并标注「用的是哪套、另一套会怎样」，不要停在「不知道你要哪套」上。
- **ISO 语言 / 地区代码直接识别，不自作翻译或猜测映射**：`te-IN` / `ta-IN` / `ml-IN` 等代码按原值处理与呈现；缺代码 ↔ 中文释义映射时，保留原代码并标注「未确认中文名」，不要编造中文名或自行翻译。
- **报告语言跟随用户提问语言**：用户用中文问就用中文交付，用英文 / 本地语言问就相应语言交付；数据里的本地语言代码（如 `te-IN`）保留原值并附简短中文释义，不要整篇机器翻译导致代码失真。
- **非中文（含本地语言）提问同样适用本技能全部纪律**：数据 100% 忠于给定口径、歧义说明清楚，不因提问语言不同而放松。
- **地区字段口径仍以 `countryCode` 为准**：`localeIso3Country` / `ipCountryCode` / `networkCountryIso` 是推断口径（见「本连接器已知事实」），与注册国不一致，不要因名称含 locale / country 就当作语言或国家口径混用。

## 注意

- 经营数字只从本技能对应的数据连接器取。其它资料库里的文档不能用来证明这个数不存在。
- 工具返回报错（5xx / 超时 / 连接失败）是**上游故障**，不是数据缺失——如实说「查询失败，没能取到」，不要说成「库里没有这个数」「数据源没这个数」；能换一个来源重试就重试一次，仍失败就交代故障本身，不要把故障译成缺数。
- 本轮工具通道里没有该数据源时，要说「这次对话没有启用对应数据源」，不要说成「系统没有接入」或「账上没有这笔数」，也不要改用其它域补一个数字。
- **口径遵循铁律（最高优先级）**：业务口径以用户或既有定义为准，**不要自己发明或改写口径**。用户**显式**给定了表 / 字段 / 去重主体（guid 还是 uid）/ 去重函数（uniq 还是 uniqExact）/ 分组形态 → **严格照做**，任何示例、任何内部默认纪律（含「本连接器已知事实」里的默认口径）都**不得覆盖**用户给定口径；用户未给定时，才回退到技能默认（如账号口径、趋势近似）。改写用户给定口径（如把 `uniqIf` 改成 `uniqExactIf`、把 `guid` 换成 `uid`、把用户指定的表换成另一张）即使方法论更优，也会偏离用户基准，一律禁止。
- **多口径 / 多表冲突要透明选择，不要悄悄替换**：当多个来源 / 表能给出同一数字但口径不同（如明细表 vs 预聚合中间表、设备口径 vs 账号口径）时，**选最可靠的一个作为主口径并明确说明弃用了哪个、为什么**（例如过期预聚合表只覆盖部分时段、设备口径会因一号多机放大）；绝不把某一套口径静默当标准答案。用户未指定表时，优先走已验证的明细 / 主表，慎用 `metabase_upload` 等预聚合中间表，用之须声明其覆盖时段与口径局限。
- **歧义与缺映射时先交付能答部分，不交白卷**：映射缺失 / 口径不确定（如影片类型中文名 ↔ 代码无字典、语言字段有两套标准）时，**先以最贴近的可得口径把能算的算出来并交付**，同时显式列出「假设了什么、缺什么、按另一口径会怎样」；不要卡住等确认、不要擅自选一个「更常见的」口径当标准。四类不确定要分别标注：口径不确定（说明可选定义）、数据不确定（部分周期 / 数据未同步完）、统计不确定（小基数，变化率不做强度解读）、分析不确定（只说伴随因素，不编因果）。
- **小基数隔离**：分组样本量极小（个位数 / 两位数）时，变化率、占比不做强度解读，单列标注；跨基数数量级差异大的分组（如某语言组几千 vs 另一组几十万）不可直接横向比强弱。
- 同一轮里已经确认过的数字不要重复查询，直接复用。
- 涉及个人信息列（手机号/邮箱/证件号/银行卡/薪资等）时，默认只做聚合统计、不返回明文明细；确需明细请走脱敏通道并确认已授权（查询前体检会提示疑似敏感列）。
- **指标契约（metric contract）：核心指标口径必须显式声明**：会员存量、日活、流失结构、首充付费转化、获客渠道这类高频指标，回答时必须写明其口径契约——实体、过滤条件、时间窗与时区、去重键（guid 设备 / uid 账号）、去重函数（uniq 近似 / uniqExact 精确）、来源表。多个既有定义冲突时，选最可靠的一个作主口径并声明弃用了哪个、为什么（见「多口径 / 多表冲突要透明选择」）。**优先复用已验证查询 / 现成 Metabase 卡片**——现成定义已经过核验，直接复用比每次裸写 SQL 更准、更快、口径更稳；没有现成定义才自己写。
- **增减结论必须带瀑布，归因须有维度支撑**：出现"增长 / 下降"结论时，必须给出期初、期末与分解项（新增 / 流失等），对不平就降级为"初步"。没有维度查询支撑的归因叙述（如"因新客下跌""因流失加剧"）一律标为「假设」，不要当确定结论写进交付。
- **多子问题先列清单、收尾前逐条覆盖**：用户一次问多个子问题时，先列出子问题清单；收尾前每个子问题要么至少查过一次、要么写明查不了的原因；剩余预算优先给还没覆盖的子问题（避免"有证据就收尾"却漏掉某个子问题，把没答的当成"库里没有"）。
- **反向接地核验**：若回答写"未取到 X / 没有 X"，但本轮工具结果里其实已有 X 的数据，判为未接地，应回补说明，不要把"其实取到过"说成"没取到"。
- **元数据缺列兜底**：技能里引用的列在 `get_database_schema` 中找不到时，先用 `DESCRIBE <table>` 确认（Metabase 元数据常同步不全，实测会员表只返回 7 列、`DESCRIBE` 实际有 15 列），不直接下"没有该列"的结论；确认字段确实存在后再据其取数。

## 被专名护栏挡住时的恢复步骤

本连接器的取数请求里常带内部业务编码（如渠道码 `INGoogle8`、表名/字段名）。服务端有一条「专名护栏」：在**未读过本技能、且未做过公开检索**前，调用 BI 工具会被附加一条提示（**不再阻断**——只读查询 fail-open，照常执行）。若你遇到「提示先 web_search」而卡住取不到数，按下面走：

1. **先读完本技能**（`read_skill business-data-query`）：读完技能后护栏自动放行，无需先检索。
2. **若已经 `web_search` 且无命中，不要据此放弃**：公开检索无结果只说明外部世界没有这个主体，不代表业务库里没有。回到本流程，基于内部表/字段直接取数。
3. 仍取不到时按步骤 7「某个维度实在取不到时」处理（先全集群扫列确认，再如实说明试过哪些来源）。
