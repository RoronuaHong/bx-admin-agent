# 业务取数流程

适用场景：用户要一个业务数字，而答案必须来自真实数据。这是本助手最高频的任务，也是最容易出错的一类：**数字看起来合理就没人会去核对**，所以错口径会被直接带进决策。

流程固定为「先确定问的是什么 → 找存量口径 → 取证 → 取数 → 核对 → 交付」。每一步都有明确的产出，跳过任何一步都可能让后面白做。

## 步骤

1. **先确定问的是什么**：把口径写成三个问题——时间范围（哪天到哪天）、粒度（按天 / 按渠道 / 按用户）、过滤条件（哪条业务线、哪些状态）。三者都会改变结果。
   - 用户没说、且不同解释会给出**不同数字**时，用 `request_clarification` 给互斥选项让用户选，不要自己挑一个"更常见的"。
   - 判据：**能不能举出第二个说得通的解释**——能，就问；举不出，才直接执行。
2. **先找存量口径，再写新查询**：用元数据 / 搜索类工具找同一口径的既有定义（已保存的提问、仪表盘、卡片里的 SQL）。有现成的就以它为基准——同一个指标出现两套算法，比数字本身错更难排查。
3. **陌生表先取证，别靠字段名猜**：
   - 读元数据（表/字段描述、语义类型、外键指向）；描述缺失时以数据为准，并说明依据来自数据而非文档。
   - 需要看真实取值就取取值域（如 BI 适配器的 `get_field_values`；没有该工具就用最小聚合查询）。**取值域里出现的值就是真实存在的取值**，不要因为"看着像脏数据"就顺手过滤掉——要排除必须给出业务理由并写明口径。
   - 表关系不确定时先跑单表口径，再跑关联口径；两者不一致就查清差在哪，不要默认关联后的结果才对。
   - 主键 / 唯一性别靠命名猜：用 `count(*)` 与 `count(distinct …)` 验证候选键。
   - 结构探查结果很大时，委派子代理专门做"探 schema"，只把结论带回来，避免把大量原始结构灌进主上下文。
4. **查询只读、最小代价**：先加 `LIMIT` 把假设证伪，再跑完整聚合；在查询侧完成聚合与过滤，不要把明细行搬进上下文（既慢又贵）。写操作会被硬拒——取数只需要只读查询。
5. **交付前自己核对一遍**：量级对不对（与总量或上次同类结果比）、口径是否就是用户问的那个、有没有 NULL / 空串被静默排除。对不上就查清差在哪，而不是挑一个看起来合理的数字报出去。

## 交付格式

- 第一句给结论：**数字 + 口径**（时间范围 / 粒度 / 过滤条件）。
- 第二句给来源：用了哪张表，或复用了哪个既有定义。
- 可能影响解读的点如实说明（例如"已排除 status 为空的 3 条记录""该字段存在默认值"）。
- 用户要图时再出图；要明细时再给明细行。

## 注意

- 查不到就如实说查不到，不要用其他域的数据或训练记忆补全——这比"没有这个数"更有害。
- 业务口径以用户或既有定义为准，不要自己发明口径；用户说了口径就按用户说的算。
- 同一轮里已经确认过的数字不要重复查询，直接复用。
